# Viva 主 agent 路由可行性验证

[English](agent-routing-feasibility.md) | 简体中文

日期：2026-11-09。对应[路由与任务调度方案](agent-routing-design.zh-CN.md)。验证基线为 `0fc159bd8dbbb42bfbcf05ee5f9150dbb9df426b`，模型使用本机已有的 `deepseek-official / deepseek-flash` 接入，DSH 目录显示名为 `DeepSeek-V41-Flash`。复用现有环境密钥，不读取或修改日常 Viva 的数据和配置；“本机已有接入”不表示模型权重在本机运行。

**结论：运行时机制具备可行性，但当前路由协议与提示尚未达到实施验收要求。** 机制实验 12/12 通过；真实模型正式样本 22/27 通过结构化契约断言。五次未通过均保留原始输出，不能将“模型说得对”直接当作“后端可以可靠继续处理”。

## 1 方法和证据

验证源码位于 [隔离探针](../test/fixtures/routing-feasibility/run.ts)、[路由插件](../test/fixtures/routing-feasibility/index.ts)和[契约与提示](../test/fixtures/routing-feasibility/contract.ts)。它们不是产品实现，未加入生产 profile，CLI 不匹配 `.test.ts` 自动发现规则。完整结果、动作、关键事件、源码哈希和探索期失败保存在[机器可读结果](agent-routing-feasibility-results.json)。

每次运行使用私有临时目录、新的 DSH home、工作区和 session。所有请求、历史和任务材料都是合成资料。实际任务会话使用仅等待后返回固定标记的安全工具，不执行真实市场调研或写用户文件。

机制组使用真实 DSH 与模拟模型，四类场景各三次。正式模型组包含九类场景各三次，共 27 次；普通流式回答、检索和工作任务内部可能有额外模型步骤，27 不代表 HTTP 调用总数。另有三次并发追问，是对应并发场景内的后续请求，不另充当独立通过样本。

正式历史样本先生成 80 轮合法的合成会话事件，落盘、关闭并恢复 session。三次真实模型请求均在第 81 轮处理。检索场景只把原文放在探针历史工具中，要求按需查找和读取。两种场景均允许读取原文回退；未证明模型仅凭压缩后的内部上下文就能完整记住全部约定，也未测试生产 FTS 的召回率。

## 2 运行时机制结果

| 场景 | 结果 | 直接证据 |
| --- | --- | --- |
| 首轮只输出正文，没有路由 | 3/3 | 正常结束前触发一次补交；提交 reply 后下一步骤有可见文本 |
| 全局与 scope 内越权工具 | 3/3 | 工具范围被收窄；两个直接执行探针均被拒绝，陷阱工具正文从未执行 |
| 提交 start 后结束当前轮 | 3/3 | 真实工作 session 被创建；主会话先于工作任务结束 |
| 连续不提交路由 | 3/3 | 恰好两次补交后报告失败，未提交正文没有进入探针可见输出 |

主会话实际工具清单只有历史、任务查询、相关文件读取和 `commit_route`；专门注册的 scope 越权工具虽可见，执行仍被 guard 拒绝。工作会话只拿到安全步骤工具，没有主会话路由工具。该结果验证工具可见性与执行检查需要同时存在。

流式验证记录了路由步骤和文本步骤：`reply` 接受后在后续模型步骤产生可见增量。抑制未提交文本的是探针的事件门控和可见输出收集器，尚未接入 Viva 的实际 renderer；不能据此宣布产品界面已经具备门控。

## 3 真实模型正式结果

| 场景 | 契约通过 | 主会话用时中位数 |
| --- | --- | --- |
| 主动交接完整简报委托 | 3/3 | 6.408 秒 |
| 修改已有简报任务 | 3/3 | 4.257 秒 |
| 修改简报同时新建行情分析 | 3/3 | 3.545 秒 |
| 同名报告的模糊指代 | 2/3 | 4.685 秒 |
| 普通回答先路由后流式输出 | 3/3 | 2.631 秒 |
| 恢复 80 轮历史后制作简报 | 3/3 | 5.229 秒 |
| 按需检索旧标准再制作简报 | 2/3 | 5.695 秒 |
| 助手建议未得到用户确认 | 0/3 | 8.827 秒 |
| 任务运行时同一会话继续追问 | 3/3 | 3.979 秒 |
| 合计 | 22/27 | 4.685 秒 |

主会话用时为提交当前请求至当前主会话轮结束，包含必要检索、路由和普通回答生成，不包含等待工作任务完成。样本范围为 2.180 至 12.398 秒；这是小样本实验，不是延迟承诺或可靠性统计。

并发组提供了完整材料与 `report.md` 输出要求，工作工具等待 12 秒。三次后续追问均在原主会话内正确复述刚才的委托，并在任务结束前完成；追问耗时分别为 1.396、3.499、2.178 秒。这里验证的是会话分离和上下文连续性，不是文件真的写出。

任务补充、停止和澄清等决策在探针中主要记录为结构化计划；没有实现新的生产请求存储与所有动作适配。既有任务运行时和通道的回归结果见第 7 节。

## 4 五次未通过的实际原因

**四次以 reply 表达澄清。** 同名报告场景一次、未确认建议场景三次，模型都没有贸然选择对象，也没有把助手建议当成用户确认。它们的自然语言说明是正确的，但提交动作是 `reply`，后端无法据此建立 `clarify` 问题、等待状态和回答关联。

未确认建议组的 0/3 是结构化协议失败，不是三次误采纳助手建议。原始自动断言的简短标签过于粗略；结果 JSON 保留这些标签，并以 `reviewedFailures` 补充人工逐条复核，未改写原始输出。

**一次仅恢复标准而漏交执行。** 模型正确找回相关性排序、中文和识别码 `ROUTE-JADE-7391`，但只提交 `reply` 说明标准，并再次询问用户是否开始。用户已经要求制作简报，恢复背景只是中间步骤，最终交付动作缺失。这不应诊断为没有找到旧上下文。

这些结果说明 `commit_route` 和合法 schema 只能保证有结构化出口，不能独自保证动作类别和用户目标覆盖正确。普通 reply 仍然可以包含未被宿主持久化的澄清，或替代原本应该交接的工作。

## 5 实施前需要修正的设计

1. **明确回复与澄清的契约。** 需要用户提供信息或选择对象时，必须提交可持久化的问题及关联处理项，不能只把问题写在 reply 正文里。完善工具 schema、提示示例和验收；不能仅靠正文中是否有问号进行硬判断。
2. **检查原请求目标是否全部有去向。** 把“找回标准”和“按标准制作简报”分别识别为上下文步骤和交付要求。决策中明确已处理、已交接、等待输入或尚未处理的部分。结构化覆盖字段仍由模型填写，不能因此声称语义正确率得到程序保证。
3. **限制重复检索。** 正式样本中，有的简单路由搜索最多 8 次；未确认建议样本为 4 至 6 次搜索及一次原文读取。增加工具查询去重、读取与 token 预算，以及空结果后的策略。预算耗尽应如实报告或提出澄清，不编造背景。
4. **以失败回归决定是否增加复核。** 固定当前五次失败为语义与结构化契约用例。若更清晰的协议仍不稳定，再评估对“需要输入却提交 reply”或“恢复背景后结束”的情况增加语义复核；不要默认对所有消息无条件再加一次模型调用。

修订后需要重新重复全部九类真实模型用例，并保留本轮失败作为对照。不能仅重跑原用例直到得到通过，或用模拟模型替代语义验收。

## 6 开发期失败和样本调整

所有探索记录在结果 JSON 中保留，正式通过率只使用最终指定样本。

| 记录 | 原因和处理 |
| --- | --- |
| 首轮机制探针全部在请求前失败 | 实验插件缺少 version，DSH 插件清单扩展拒绝准备请求；补齐元数据，没有把它当作模型失败 |
| 初次 80 轮种子出现 token meter 错误 | 历史 assistant 事件缺少对应 step/start；补齐合法边界 |
| 早期种子能运行但当前轮仍编号 1 | 驱动器在注入历史前已建立计数；正式样本改为落盘、关闭和恢复，核实当前轮为 81 |
| 早期并发请求要求检查“样例材料”但没有提供材料 | 两次模型合理澄清；该输入不适合断言必须启动任务，正式用例改为明确材料和文件交付要求 |

原模糊指代和未确认建议的结构化失败没有通过重跑替换。正式上下文与并发组只替换了不满足所测前提的实验设置，保留了其全部记录与解释。

## 7 回归与覆盖边界

相关既有测试共 48 项通过：`tasks-plugin.test.ts`、`task-runtime.test.ts`、`steer-plugin.test.js`、`steer-reports-dsh.test.ts`。完整 `npm run typecheck` 通过，新增探针在 `tsconfig.test.json` 的 strict 检查范围内。

此次验证未完成生产 UI 门控、请求和动作的正式数据库迁移、应用操作审批解耦、角色在所有恢复路径上的重绑、真实 FTS 召回质量、图片接入、崩溃后的动作核实或 macOS 与 Windows 全链路验收。实际工作任务只调用安全步骤，不代表研究报告质量、金融信息正确性或文件交付已验证。

本轮证据足以支持继续修订并实施隔离的 R1 原型，不能作为完成 R1 至 R3、批准生产切换或完整上线的依据。是否开始实施仍需用户对方案修订确认。

原工作区有两份未登记的 `memory-design` 草稿，与本 PR 无关，保留其正文和登记状态。PR 在独立 worktree 中只收录本次方案、报告、证据和探针；该精确文件集合的完整 `npm test` 为 1162/1162 通过，`npm run typecheck`、`npm run check:i18n` 和 `git diff --check` 均通过。

## 8 复现

在仓库根目录使用现有环境密钥运行。脚本默认创建新的私有临时目录，最后打印报告与事件位置；不要复用日常 Viva 的 DSH home。

```sh
# 真实 DSH 与模拟模型，不调用付费模型
ELECTRON_RUN_AS_NODE=1 ./node_modules/.bin/electron test/fixtures/routing-feasibility/run.ts --repeat 3

# 真实 DeepSeek v4.1 接入，仅合成数据；当前协议预期会暴露失败
ELECTRON_RUN_AS_NODE=1 ./node_modules/.bin/electron test/fixtures/routing-feasibility/run.ts --live --repeat 3

# 只验证正常恢复后的 80 轮历史
ELECTRON_RUN_AS_NODE=1 ./node_modules/.bin/electron test/fixtures/routing-feasibility/run.ts --live --repeat 3 --only history-80-session
```

`--out` 可指定新的实验输出目录，`--only` 接受逗号分隔的场景 ID。真实模型会产生调用费用。密钥只在内存和子进程环境中复用，不写进报告或命令行参数。
