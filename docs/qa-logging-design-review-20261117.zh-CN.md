# Viva 日志方案评审记录

评审对象为 [日志与故障诊断方案](logging-design.zh-CN.md)及其[英文版本](logging-design.md)。日期为 2026-11-17。

本轮只编写与评审方案。运行时代码、故障复现和跨平台发布验收尚未实施。

## 评审范围

- 对照当前代码确认 memory:get、dream、恢复与请求屏障的语义。
- 检查架构分层、独立插件打包、调用关联和完整主线覆盖。
- 检查超时与取消、日志容量、故障隔离、导出、隐私和遗忘。
- 检查实施顺序和可执行的验收标准。

## 第一轮独立评审

两位子 agent 分别评审架构语义与故障边界。初审均未通过，共提出 6 项 P2 问题。

| 问题 | 修订 |
| --- | --- |
| 前台事件缓冲缺溢出与必要快照失败语义 | 规定数量、字节、年龄和初始化期限，失败停止积压并以新 generation 重同步 |
| 诊断端口异常可能改变业务结果 | 同步非抛出端口与安全适配器，初始化/异步失败在诊断层降级 |
| 文件 I/O 永久 pending 未受导出期限覆盖 | 包含在途字节的队列、单个在途 I/O、独立导出子进程与 30 秒总 watchdog |
| 活动文件与导出固定范围绕过配额 | 100 MiB 硬预算含所有文件槽，导出单实例、固定范围/临时文件有界、异常退出保守计账 |
| 未知 Error.name、函数和模块符号可能含正文 | 未知错误固定枚举，只接受构建清单可验证的静态帧 |
| 超时后合并表和并发占位可能阻塞重试 | 释放调用方占位并移出合并项，服务端未结束名额独立有界，首次超时允许一次独立重试 |

全部修订保留 L1、L2、L3 三阶段，补入对应回归验收，中英文同步更新。

## 第二轮独立复审

故障边界评审通过。架构评审另发现 2 项 P2，均来自上一轮新增的恢复和限额规则。

| 问题 | 修订 |
| --- | --- |
| 本地初始化 generation 不能区分同会话旧推送 | 明确业务 streamGeneration、eventCursor 与必要快照 cutoverCursor，不借用日志 traceId；边界不明则明确失败 |
| 超时删除 waiter 后缺少真实读取结束确认 | readBatchId 归可信业务协调层，迟到终态先结算执行再判断 UI waiter，补两次超时后完成、第三次成功的验收 |

## 用户补充约束

用户要求优先成熟日志框架、控制性能影响，并支持日志环绕。方案选用 Pino 与 SonicBoom，复用 JSON/级别/child logger/serializer/redact/异步写入/目的端生命周期，业务侧只保留薄环绕和策略适配。补充 AsyncLocalStorage、同步/异步环绕行为、两层缓冲合计上限、隐式退出同步刷盘防护与性能验收。首版不安装依赖或修改运行时代码。

## 第三轮独立复审

架构评审通过。故障边界评审针对新增框架提出 3 项 P2。

| 问题 | 修订 |
| --- | --- |
| 编码上界预留与 write 释放不对账会泄漏预算 | destination 按实际编码退差额，过滤/失败/drop/部分write/error分别结算，背压不等于drop |
| reopen ready 不证明旧fd关闭 | 受管轮转使用end后等待close再创建新目的端，未确认关闭保留资源占位 |
| 库内 EAGAIN/EBUSY 重试及flush的fsync可能挂起 | retryEAGAIN明确结束库内持续重试，周期flush不用回调，生命周期flush与fsync受统一期限限制 |

## DSH 能力核对

用户补充要求复用 DSH 诊断规范，并限于客户端本地。新增专门子 agent 只读核对锁定依赖中的公开文档、类型和源码。方案补充 Cordis logger/exporter、tools/execute官方环绕、公开Agent/工具/Session事件、原生日志/telemetry与业务诊断的边界，禁用deprecated hook，区分emit/waterfall/serial。明确FEEDBACK_ONLY不是本地模式，受管profile禁用独立上传路径，原生正文/启动报告/fetch capture不自动入包。

## 追加独立复审报告的审视与修订

对照[追加独立复审报告](qa-logging-design-independent-review-20261117.zh-CN.md)、当前方案以及 host 命令解析、owner 通道和启动路径，确认两项 P2 与两项 P3 均值得处理。原始评审意见保留，四项处理状态已回填到该报告末尾，不改写其静态评审结论。本节记录主 agent 的逐项判断，不将此前子 agent 的通过结论冒用于本次修订。

| 报告问题 | 判断与方案调整 |
| --- | --- |
| P2 诊断元数据校验失败影响业务 | 采纳。独立可选有版本envelope，业务与诊断分别safeParse；非法诊断丢弃并计数、业务照常。认证、业务协议、输入和传输限制仍严格校验。纯日志字段不提升MEMORY_HOST_PROTOCOL；不新增旧业务/旧数据兼容 |
| P2 L1业务改造与诊断交付绑在一起 | 采纳分批验收。保留L1/L2/L3，L1内部为L1a只读诊断、L1b可用性修复、L1c加固。L1a保留全部基础安全保护、独立插件打包和基础性能对照，L1c做故障/平台验证；不会先交付无界队列或未脱敏日志 |
| P3清空后沿用诊断盐 | 采纳并限定语义。清空轮换盐和diagnosticRunId，失效旧child绑定、缓存和别名；不改应用身份/owner epoch/真实执行名额。停写与删除未确认时报告cleanup_pending，已导出ZIP不改写，不承诺元数据匿名 |
| P3活跃JSONL尾部半行 | 采纳。只导出完整换行记录，分别记录原始截止、实际源范围、残片和重编码输出大小；UTF-8残片不误判为损坏，完整但非法的记录独立计数 |

对应补充元数据降级/业务拒绝、执行中清空与旧代次迟到、尾部半行/UTF-8及分批验收用例。Pino/SonicBoom选型、DSH公开环绕、本地诊断和三阶段总体范围保持原定方向。本轮只修订中英文方案及文档登记，没有安装依赖或修改运行时代码。

## 第五轮追加修订复审

处理状态：本节两项问题已按下方“第五轮处理结果”修订到中英文方案，待实施验收与独立复核。以下保留发现问题时的原评审意见，不将方案修订标为运行时验证通过。

基于上一节更新后的中英文方案，再次静态核对诊断元数据隔离、L1分批、清空代次及JSONL导出规则，并对照当前loopback HTTP传输实现。最新结论为暂不通过：未发现新增P0/P1，但仍有1项P2设计缺口和1项P3验收缺口。此前各轮结论保留为历史记录，当前方案是否可进入实施以本节未闭合问题为准。

| 问题 | 证据与判断 | 待修订 |
| --- | --- | --- |
| P2 诊断envelope仍可因传输限额改变业务结果 | 方案第4节先执行既有传输大小限制，再分别safeParse业务与诊断；L1a却要求启停诊断不改变业务返回和准入。当前`src/backend/rpc-server.ts:42-64`在JSON解析前累计完整body并在超过32 MiB时返回413。因此接近上限的合法业务请求附加诊断后可能被拒绝，超大非法诊断也无法进入safeParse降级路径 | 发送端分别计算业务与诊断的编码字节，加入诊断会超过既有限额时丢弃诊断并计数，按原大小发送业务。明确整个消息已超传输上限时接收端只执行传输准入、不承诺恢复业务。补诊断开关下恰好上限、多1字节、多字节UTF-8及超大非法envelope用例 |
| P3 完整换行但非法JSON的记录缺少验收用例 | 方案第10节要求此类记录计为invalid_record且不复制原文，但第13节JSONL用例只覆盖半行、UTF-8半字符、未完成首行和崩溃尾部，未验证完整非法记录 | 增加含秘密哨兵的完整非法记录，前后各放合法记录；验证秘密原文不进入ZIP、invalid_record正确计数、后续合法记录仍导出，且不误记为partial_trailing_record |

L1a/L1b/L1c分批验收及清空时轮换盐、diagnosticRunId、失效旧绑定的修订未发现新问题。JSONL尾部残片规则本身成立，但需补齐上述完整非法记录验收。中英文方案关键约束一致；本轮只更新评审记录及文档登记，不修改方案或运行时代码，故障注入与性能验收仍未实施。

### 第五轮处理结果

2026-11-17 主 agent 对照当前代码核实。readBody 在 JSON.parse 前累计 Buffer 字节并于 size > 32 MiB 返回413，发送端当前以Buffer编码完整请求，因此仅依靠safeParse隔离无法保证业务消息的传输准入不变，P2成立。第10节已有invalid_record语义，但验收矩阵缺少完整非法JSON夹在合法记录中间的情况，P3成立。

| 问题 | 处理状态 | 修订与验收位置 |
| --- | --- | --- |
| P2 附加诊断突破传输限额 | 方案已修订，待实施验收 | [第4节](logging-design.zh-CN.md#4-事件契约和关联)增加发送端实际编码字节预算，超预算或诊断校验/编码失败时只丢诊断并发送原业务。接收端保留完整消息限额，已超限时不承诺恢复业务。复用业务编码，不增加大对象遍历或放宽上限；[第13节](logging-design.zh-CN.md#13-验收矩阵)补精确边界、额外1字节、多字节UTF-8、转义及超大非法envelope |
| P3 完整非法JSON缺验收 | 方案已修订，待实施验收 | [第10节](logging-design.zh-CN.md#10-心跳与导出)及[第13节](logging-design.zh-CN.md#13-验收矩阵)补合法A/含秘密的完整非法记录/合法B，验证invalid_record=1、后续合法记录继续导出、原文不入ZIP/manifest，且无残片时partial_trailing_record=false |
