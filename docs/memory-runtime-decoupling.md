# Full Runtime Decoupling Plan: Agent Runtime and Memory System

[中文](memory-runtime-decoupling.zh-CN.md)

**Status: Design proposal (phased implementation pending).** 2026-11-24. Baseline: `main` after PR #175 (memory sidecar & history decoupling) and `fix/memory-sidecar-lifecycle`.

## 1. Goal and Boundary

Once fully decoupled, **the Agent runtime focuses on finishing the current task, while the memory system organizes past information into queryable reference material**. The two runtimes communicate only through persisted session events and memory APIs, managing their own processes, storage, model clients, and restart lifecycles independently.

| Interaction | Target Behavior |
|---|---|
| **Agent supplies memory material** | Verified human originals, open-ended answers, and turn completion records are persisted first; memory reads them asynchronously from its own cursor. Session ID, turn, and source ID handle verification and deduplication across restarts. |
| **Agent uses memory automatically** | Static rules and cached user profile are available locally in 0ms. Per-turn retrieval starts early in parallel at request entry, races against a short budget before request assembly, and returns an explicit 5-state status (`hit` / `empty` / `skipped` / `timeout` / `unavailable`). The context sent for a turn stays frozen as a snapshot; later turns see newly updated memory. |
| **Agent queries or writes explicitly** | Explicit tool calls (`memory_recall` / `memory_read` / `memory_node_search` / `memory_remember`) and user management actions run within their own budgets and return explicit statuses on failure or offline state so the Agent can proceed or ask the user to confirm. |
| **Memory background consolidation** | Daily notes, Dream, and indexing are scheduled by the memory plugin's private `memory-worker`, reusing DSH's `ctx.llm` as the single system-wide LLM gateway, with serial execution, 429/5xx backoff, and soft foreground yielding to govern shared provider quotas. |

### Three Remaining Coupling Points After PR #175

PR #175 already removed synchronous send fences, host erasure cascades, and native session rewrites. Only three direct couplings remain:

1. **Automatic retrieval still blocks `agent/pre-step` via a synchronous `await`**, bundling static rules, user profile, and dynamic file retrieval into one cross-process RPC.
2. **Hosting `memory-worker` under the Viva main process creates a dual-child relay and splits Viva (`fromViva`) from standalone DSH**, resulting in three-process Note / Dream round-trips (`memory-worker ↔ Viva backend ↔ DSH`).
3. **Ingestion still races across two channels**: the DSH plugin scans session logs for `receiveSource`, while Viva's backend sends `sourceAlias` and `acceptQuestionAnswer` over a separate fire-and-forget IPC channel.

The following sections break the work into four independently deliverable phases.

## 2. Phase 1: Automatic Memory Injection Refactor (3-Layer Split + Early Short-Budget Race + 5-State Protocol)

### 2.1 Timing Budget and Current Bottlenecks

- Local Agent request assembly (`preStep` → `assemble` → `buildRequest`) typically takes **5–20ms**.
- Cross-process IPC + SQLite FTS5 + Markdown verification takes **20–60ms**; adding the ONNX embedding child process (`memory-embedder-worker`) takes **40–150ms** warm and often **>200ms** cold.
- Starting retrieval inside `agent/pre-step` with a 0ms wait means the first turn will almost never catch the result, causing missed implicit conventions (e.g., "send weekly reports to B from now on") or forcing an extra tool round-trip.
- Bundling `MEMORY_RULES`, user `profile`, and dynamic retrieval hits in one `systemPrompt.context('viva-memory')` also duplicates static rules and profile into conversation history on every turn whenever hits change, wasting tokens and hurting prompt-cache stability.

### 2.2 Three-Layer Split

| Layer | Content | Change Frequency | Delivery | Latency |
|---|---|---|---|---|
| **L1 · Static rules** | `MEMORY_RULES` (tool usage, non-instruction rule, timeout/offline guidance) | Static | Registered by [adapter.ts](../plugins/memory/lib/adapter.ts) as a static header `systemPrompt.section` | **0ms** (full KV-cache hit) |
| **L2 · User profile snapshot** | Resident user profile summary body + today's date | Very low (profile change or day rollover) | Pushed by memory worker on `ready` and profile updates as a schema-agnostic text snapshot `{ epoch, revision, text }` and cached in the host; replayed directly on DSH `attach`, combined locally with today's date, and rendered as the sole `systemPrompt.context('viva-profile')` (date-only or empty when `text` is empty or before cold-start worker readiness) | **0ms** (survives independent worker or DSH restarts and search timeouts; swapping the profile backing store later requires zero L2 protocol changes) |
| **L3 · Per-turn retrieval** | 1–3 relevant `daily/digest` snippets or status hint for the current turn | Per turn | Started early when building the final validated delivery + raced against a tight remaining budget; appended in `agent/pre-step` via `decision.messages` as an attributed `source: { kind: 'viva-memory' }` message (`<memory-recall turn="N" ref="<requestId\|messageId>">`), outside `systemPrompt.context` | **Bounded (candidate 120–150ms, tuned via dual-metric benchmark)** |

### 2.3 Early Kickoff, Delivery Binding, and Fast/Slow Path Separation

1. **Early kickoff, exact binding, and task header propagation in Viva desktop**: start prefetch in [acp-bridge.ts](../src/backend/acp-bridge.ts) right when constructing the final validated request—covering foreground `prompt`, `agent:steer`, and scheduled/background task `preparePrompt` / `steerTask`. Once `requestId`, target `sessionId`, and host-verified query text are known, kick off an asynchronous worker search and record `(requestId, sessionId, deadlineAt, ownerEpoch, revision)` **without waiting for `sourceAlias`**, overlapping ACP transport, inbox queueing, `tools.resolve`, and `systemPrompt.assemble`.
   - **Carrying task `requestId` while preserving verbatim task text**: task sessions stay separate from `viva-routing`'s main-session `【请求 ID：】` ledger by wrapping `preparePrompt` / `steerTask` with a lightweight, routing-independent task reference header (reusing the zero-width escaping and `spans` computation from `src/shared/request-routing/header.ts` to produce `{ requestId, wireText, spans }`). `acp-bridge.ts` passes the clean `text`, `wireText`, and `wireSpans: spans` to `recordSource` (so memory intake restores the verbatim headerless task text via `spans`) while registering the host prefetch under `(requestId, sessionId)`. DSH `pre-step` parses `requestId` from the message and claims strictly on `(requestId, sessionId)`—never matching by text content and discarding late results from rebound sessions.
2. **Feed continuation, no-query, and credential-skip boundary (`skipped` status)**: during Feed validation, explicitly extract the user's addition and pass it down as `sourceText` (explicit empty string `''` for a pure draft, never `undefined`). Host prefetch and standalone DSH fallback share the same admission gate: run automatic retrieval only when the effective user text (`sourceText !== undefined ? sourceText : text`) is non-empty and does not match `looksSecret(question)`. For pure drafts, image-only prompts, or credential-bearing inputs, skip retrieval and record a claimable `{ status: 'skipped' }` terminal entry (remaining silent even on late claim, never calling retrieval or appending L3, and separating unexecuted lookups from completed zero-hit `empty` searches in metrics).
3. **Claim precedence: valid completed terminal result before deadline (no dropped hits and no double budget)**:
   - **Step 1 (prefer valid completed terminal result)**: if `(requestId, sessionId)` already has a **still-valid terminal result completed within budget** (`hit` / `empty` / `skipped` / `unavailable`), **consume it immediately in 0ms even if claimed after `deadlineAt`**, with no extra wait and no second search;
   - **Step 2 (apply `deadlineAt` only when unfinished)**: if still pending and before `deadlineAt`, wait only until `deadlineAt` (aborting the worker search and recording `{ status: 'timeout' }` on expiry); if `deadlineAt` has elapsed or `{ status: 'timeout' }` is recorded (retained until claimed or TTL-evicted, e.g., 60s), **consume `timeout` immediately in 0ms with zero second lookup**;
   - **Step 3 (fallback only when genuinely unprefetched)**: only verified inputs that had **no prefetch** (rebound queued prompts, multi-source replays, standalone DSH) fall back to short-budget live retrieval in [adapter.ts](../plugins/memory/lib/adapter.ts) under the same 5-state contract.
4. **Invalidation of unclaimed hits on memory changes (write-back + claim checks, zero extra I/O)**: every prefetch binds `{ ownerEpoch, revision }` at start and in its reply. When the host observes `memory_owner_change` (file edit, disable, enable, forget, Dream commit) advancing `revision`, or `unavailable`, invalidation covers both cached hits and **any in-flight `pending` lookup whose reply arrives later**:
   - Check `result.ownerEpoch === currentEpoch && result.revision === currentRevision` both **when storing a reply** and **when claiming in `pre-step`**; any mismatch immediately marks the result stale so an old reply is never cached or adopted as a valid `hit`;
   - If invalidated before `pre-step` adoption and the original `deadlineAt` still has remaining budget, run one retry within that remaining budget (applying the exact same write-back and claim checks to the retry); if stale again or out of budget, proceed immediately with `timeout`—preventing disabled/deleted content from entering a model request for the first time without adding foreground wait.
5. **Tighter vector cap inside retrieval**: in [memory-file-retrieval.ts](../src/memory/core/memory-file-retrieval.ts), give ONNX vector inference a tighter dedicated cap for automatic searches (e.g., `50–60ms`, skipping cold-start inference while warming in the background) so lexical hits reliably make the first-turn cutoff.

### 2.4 Explicit Automatic Recall Contract

Replace `string | null` with a structured `AutomaticRecallResult`:

```ts
export type AutomaticRecallResult =
  | { status: 'hit', text: string, partial: boolean, hits: Array<{ text: string, names: string[] }> }
  | { status: 'empty' }
  | { status: 'skipped' }
  | { status: 'timeout' }
  | { status: 'unavailable' }
```

- **Zero-hit completeness rule**: return `empty` only when lexical, vector (when enabled), and file verification all finish cleanly with zero hits. When lexical finds zero hits but vector inference, embeddings, or file verification time out or degrade (`partial: true`), **map directly to `timeout`** so callers and the model distinguish an incomplete search from a completed zero-hit search. Requests with no eligible query text (pure draft / image-only) or matching `looksSecret(question)` produce `skipped` and are tracked separately from `empty` and hit-rate denominators.

| Status | Runtime / Diagnostics | Per-Turn Model Message (L3) | Expected Model Behavior |
|---|---|---|---|
| `hit` | Record hit count, latency, and `partial` flag; report `memory_context` once when committed | Append `<memory-recall turn="N" ref="<id>">` snippets; if `partial === true`, add a brief note that automatic search was partial | Use directly; call `memory_recall` if uncertain |
| `empty` | Record completed zero-hit lookup and latency | **Append nothing** (zero noise) | Answer normally without redundant recall |
| `skipped` | Record unexecuted lookup (pure draft / image-only / `looksSecret` match), tracked separately from `empty` | **Append nothing** (zero noise) | Answer normally |
| `timeout` | Track timeout rate and fallback event | Append `<memory-recall turn="N" ref="<id>">`: automatic memory lookup timed out or was incomplete; call `memory_recall` if the task depends on prior conventions | Ignore for unrelated prompts; **call `memory_recall`** (wider tool budget) when prior preferences/recipients matter |
| `unavailable` | Record offline count | Append `<memory-recall turn="N" ref="<id>">`: memory service is currently unavailable | **Skip doomed `memory_recall` calls**; ask the user directly if critical info is missing |

### 2.5 Context Injection, Cross-Turn Policy, and Event Reporting Invariants

- **Physical isolation between L3 and L2**: L2 owns `systemPrompt.context('viva-profile')` exclusively; L3 stays out of `systemPrompt.context` and is appended via `decision.messages` (`source: { kind: 'viva-memory' }`) in `agent/pre-step`. Changes in L3 never trigger DSH's `RuntimeContextProjection` to re-emit the full profile or append a clearing reminder.
- **Keep historical L3 nodes across turns to preserve KV cache (Option A)**: L3 messages carry `<memory-recall turn="N" ref="<requestId|messageId>">` and state that they apply only as automatic recall reference for the referenced message, not latest state for later turns. Subsequent turns **never rewrite or replace prior `viva-memory` nodes**, keeping cross-turn prompt-cache prefixes intact; an `empty` or `skipped` next turn appends nothing.
- **Freezing begins upon snapshot adoption; parallelize multi-interjection steps under one deadline**:
  - Unclaimed prefetches remain subject to memory-change invalidation (§2.3 item 4);
  - Once Step 1 adopts L3, ordinary tool continuations (`humanMessages(decision.messages).length === 0`) are **strictly frozen**—keeping Step 1's L3 with no re-query and no deletion;
  - Mid-turn user interjections (`agent:steer`, `humanMessages(decision.messages).length > 0`): run retrieval for the new user prompt and append a new `viva-memory` message without modifying L2 or prior steps;
  - When a single step claims multiple pending interjections (`[A, B]`) from the inbox, claim/query them **in parallel under one shared step absolute deadline** (never multiplying budgets), attribute each L3 message via `ref="<requestId|messageId>"`, and append them in deterministic original order `[A, B]` even if B resolves first.
- **Commit-confirmed `memory_context` events**:
  - Remove eager `injected` emission from worker-side `fileContext()`, and do not emit before `agent/pre-step` returns (DSH still runs `prepareRequest` and re-checks cancellation afterward);
  - In `agent/pre-step`, stage pending injection metadata keyed by the L3 `UserMessage`'s unique `message.id`;
  - On `session/event` observing that exact `user/message` (`source.kind === 'viva-memory'`) **actually committed to the session** (strictly after `prepareRequest` and abort checks, immediately before `buildRequest`), claim and delete the staged entry (exact-once dedup by `message.id`) and emit `memory_context`; prune any uncommitted entries on `turn/end` and `session/disposed`. Note: this event confirms that memory entered the session, while first-request evidence coverage metrics are still measured from **actual emitted model requests**.

## 3. Phase 2: Retire Manual Profile and Switch Directly to Auto-Maintained Resident Profile

### 3.1 Rationale and Strategy

Today's L2 profile relies on users manually filling `role`, `projects`, and `preferences` during onboarding (`saveIntro`) or in About You. Starting from blank forms creates friction and quickly goes stale while splitting the mental model into a manual `profile` table and Dream-maintained `digest` files.

There are no existing users. Acceptance for Phases 1 and 2 starts from a fresh install, with no compatibility requirement for earlier databases, IPC contracts or pending operations from older versions. Phase 1’s L2 snapshot `{ epoch, revision, text }` is independent of profile fields, so Phase 2 can switch the source and remove the manual profile table, IPC and UI in one PR.

### 3.2 Single-Step Switch Scope

1. **Memory side (swap L2 content source with zero L2 transport or DSH adapter changes)**
   - **Unique global profile identity, source isolation, and L3 exclusion**: pin the resident profile to the single identity **`(USER_WORKSPACE, 'digest/personal/profile.md')`**, where `USER_WORKSPACE = memoryHash(JSON.stringify([{ kind: 'user' }, { kind: 'user' }, null]))`. Keep its L2 budget tightly bounded under one shared constant (e.g., `MAX_PROFILE_L2_CHARS = 800`, counted by Unicode code points `[...text].length`) to cross-task role context, durable preferences, and communication/output style; project-specific details and conventions stay in regular files recalled via L3.
     - **Dedicated lightweight profile pass, unified `pendingBatch` checkpoint, and commit isolation**:
       - **Ordinary Dream `consolidate` (case-insensitive read-only profile target, post-filter `hasMore` recalculation, and oversized handoff)**: define a single cross-platform helper **`isReservedProfilePath(path) => path.toLowerCase() === 'digest/personal/profile.md'`** (with the canonical write path fixed to lowercase `'digest/personal/profile.md'`). Explicitly instruct the ordinary planner that this reserved path is read-only (never `CREATE` or `REFINE`), and exclude matches of `isReservedProfilePath` from `existingDigests` catalog and `node_search` target candidates. During plan validation **before persisting `pendingBatch`**, strip every operation matching `isReservedProfilePath(op.path)` (including case variants like `digest/personal/Profile.md`) along with any subsequent operation in the same plan that depends on a stripped draft, preserving independent ordinary file operations so they commit once without retry loops, and recompute **`effectiveHasMore = plan.hasMore && retainedOperations.length > 0`** after filtering (when zero operations survive, apply baseline empty-plan semantics with `effectiveHasMore = false` so the eligible profile pass runs and advances the checkpoint; when valid ordinary operations survive and the model set `hasMore: true`, keep `effectiveHasMore = true` for multi-pass batching). The commit guard likewise enforces `isReservedProfilePath` as defense-in-depth, rejecting writes from ordinary `consolidate`, any non-`USER_WORKSPACE`, or any non-canonical casing variant (such as `Profile.md`) so ordinary digests can never occupy the path on case-insensitive volumes. When a single note triggers `context-window-exceeded` during ordinary `consolidate` (with `inputsCurrent()` true), keep recording `oversizedAny = true` and the `oversized` diagnostic (preserving the `size-limit` outcome), but **do not call `notes.markProcessed` and return early**—instead treat the ordinary pass as `operations: []` with `checkpointRefs = fileRefs` and flow directly into the dedicated profile pass and shared checkpoint path (if the profile pass itself hits single-note `context-window-exceeded`, record its diagnostic and advance the checkpoint without looping). Full daily-note batch Markdown and `read` stay unchanged so ordinary `digest/*` files continue using all eligible material (including pre-deletion sources) normally.

2. Verify disable/delete separately: ① a new session's first model request contains no profile body; ② in an existing session, the latest L2 snapshot is cleared and later steps never re-inject the old profile body (without rewriting earlier history messages);

5. ② starting after both the digest and resident profile have receipts, verify disk-unverifiable recovery and manual completion—(a) temporarily move the note Markdown file aside, run checkpoint verification once, then restore the same file: recovery finishes only that revision's checkpoint with zero extra model calls or file revisions; ## 4. Phase 3 (Revised Decision): Return Memory Worker Ownership to the DSH Plugin and Cancel the Standalone LLM Client

### 4.1 Decision and Rationale

After architectural review, both product premises behind a DSH-independent LLM client are confirmed to be **No**:
1. The "About You" memory management UI does **not** need to operate independently of DSH during the 1–2 second window when no model is configured, DSH crashes, or DSH restarts on a model switch;
2. There is no near-term plan to support non-DSH Agent runtimes or to run background memory consolidation while DSH is shut down.

Therefore, **the original Phase 3 plan (building a second LLM client and credential-sync IPC inside `memory-worker`) is cancelled**, and process ownership is consolidated back to the core model: **Viva depends on DSH, and memory is a DSH plugin that supervises its own private `memory-worker` child process**:

- **Preserve a single LLM gateway**: DSH (`ctx.llm`) remains the sole owner of provider wire protocols, DeepSeek account token refresh (`llm-deepseek-account`), proxy handling, retries, and credentials. We avoid duplicating transport plumbing (`@deepseek-ai/dsh-llm-*` are transitive dependencies and `dsh-llm-retry` is a Cordis plugin) and avoid widening the plaintext API-key exposure surface.
- **Eliminate dual-mode maintenance tax**: remove Viva's `desktop-memory-owner.ts` bidirectional relay and the `fromViva()` branch in `standalone-owner.ts` so Viva desktop and standalone DSH share 100% of the same `standaloneOwner` code path.
- **Keep process-level isolation**: the `viva-memory` plugin continues to supervise a dedicated `memory-worker` process that owns SQLite, Markdown verification, FTS5, and ONNX embeddings, preventing synchronous database I/O or embedding work from blocking the DSH main thread.
- **Retain the bulk of Phases 1 and 2**: L1 static rules, L2 local profile cache, L3 `decision.messages` anchoring with the 5-state recall protocol, fast/slow vector separation, and the full Phase 2 resident-profile + Dream checkpoint recovery design remain intact; only the Viva-hosted cross-process prefetch bridge (`memory-prefetch.ts` / `claimPrefetch`) is dropped in favor of short-budget DSH-side L3 retrieval.

### 4.2 Consolidated Architecture Boundaries

1. **Single-tree process topology**: `Viva main process → DSH process → viva-memory plugin → private memory-worker child process`. Viva supervises only DSH; Note / Dream `ctx.llm` calls stay directly between the plugin and its private worker without hopping through the Viva main process.
2. **"About You" management IPC (aligned with `viva-mcp` / `viva-tasks`)**:
   - Viva's main process forwards managed-file queries, edits, undo, enable/disable, delete, and manual Dream triggers to the `viva-memory` plugin over the existing parent-child IPC channel, which proxies them to its private `memory-worker`;
   - **Security boundary unchanged**: only the parent-process IPC channel may invoke `host` management operations; model tools and third-party plugins have no access, and the Viva main process never opens `memory.db` directly (preserving single-owner locking);
   - **Availability semantics**: while DSH is not running, crashing, or restarting, the memory channel reports `unavailable` (UI shows a transient connecting/unavailable state) and recovers automatically once DSH is ready; legacy `#161` tests asserting management availability while DSH is stopped are updated accordingly.
3. **Quota governance in place (without moving LLM transport)**:
   - **Hard concurrency cap = 1**: Note and Dream remain serialized through the existing single-loop `effects` queue;
   - **429 / 5xx backoff**: extend [model.ts](../plugins/memory/lib/model.ts) to classify rate-limit / overload responses and forward `Retry-After` into `effects` exponential backoff;
   - **Soft foreground yielding**: detect active foreground streaming directly inside [adapter.ts](../plugins/memory/lib/adapter.ts) and defer *newly started* background Note / Dream calls by a few seconds (bounded by a max defer cap to prevent starvation; never abort in-flight work, and exempt manual Dream runs);
   - **Background light-model hook**: `MemoryCompute` already passes `{ provider, model }`, allowing background stages to target a lighter model configured in DSH later.

### 4.3 Revisit Triggers

The `MemoryCompute` port in `src/memory/core/` remains unchanged. Revisit a standalone LLM client or shared LLM gateway process only if one of these requirements becomes real:
1. Background memory ingestion/consolidation must run while DSH is completely shut down (e.g. non-DSH background data sources);
2. Viva adds support for multiple Agent runtimes beyond DSH.

## 5. Phase 4: Single Source of Truth for Memory Ingestion

### 5.1 Root Cause of Remaining Races

In Viva desktop today, ingestion splits across two async channels: DSH scans session logs (`receiveSource`) while the backend fires `sourceAlias` and `acceptQuestionAnswer`. Two subtle races remain:
- A late `acceptQuestionAnswer` can be rejected if `completeTurn` finishes first and writes `owner_turns`;
- A late `sourceAlias` avoids permanent `ignored` records but still waits for `turn/end` replay.

### 5.2 Target Design

- **Persisted turn log as single source of truth (Viva desktop)**: Viva's persisted store (`history.db` or an append-only canonical turn-event table) already commits clean user originals, custom question answers, final assistant replies, `conversationId`, `sessionId`, `sourceId`, and turn numbers atomically.
- **Cursor-based async tailing**: the memory worker maintains its own cursor over that persisted stream, catching up after any restart or outage and deduplicating by `sourceId`—**eliminating `sourceAlias` and `acceptQuestionAnswer` races completely**.
- **`memory_remember` alignment**: because the user message is persisted before model execution, `memory_remember` verifies exact user text directly by `sourceId` from persisted storage instead of `sourceAlias`.
- **Thinner DSH plugin**: under Viva desktop, the DSH plugin no longer needs `ingestion.ts` scanning at all—only tool registration and context injection; standalone DSH keeps the JSONL cursor scanner.

## 6. Recommended Delivery Sequence and Verification Gates

Split into **4 independent, focused PRs** so each batch is easy to verify and roll back:

1. **PR 1 (Phase 1)**: 3-layer automatic injection + early short-budget race + 5-state protocol (highest immediate UX payoff, smallest blast radius, and establishes the schema-agnostic `{ epoch, revision, text }` L2 channel for Phase 2).
2. **PR 2 (Phase 2)**: Retire manual profile and switch directly to Dream-maintained resident profile (reuses PR 1's L2 channel, closes the UX loop early, and sheds the legacy `profile` table, IPC, and onboarding form before later runtime work).
3. **PR 3 (Phase 3 · Revised)**: Return `memory-worker` supervision from Viva's main process to the `viva-memory` DSH plugin (remove `desktop-memory-owner.ts`, `fromViva()`, and the main-process prefetch bridge to unify on one plugin path), and add 429/5xx backoff plus soft foreground yielding in place inside the plugin (may also be landed first as PR 1 before merging Phases 1 and 2).
4. **PR 4 (Phase 4)**: Single-source-of-truth persisted ingestion cursor (eliminates remaining dual-channel races and shrinks the DSH plugin).

Each PR touching main-process lifecycle, DSH plugins, IPC, or storage must pass `npm run typecheck`, `npm test`, `npm run check:i18n`, plus `npm run build` and `npm run smoke` (especially `smoke:memory`).
