# Full Runtime Decoupling Plan: Agent Runtime and Memory System

[中文](memory-runtime-decoupling.zh-CN.md)

**Status: Design proposal (phased implementation pending).** 2026-11-24. Baseline: `main` after PR #175 (memory sidecar & history decoupling) and `fix/memory-sidecar-lifecycle`.

## 1. Goal and Boundary

Once fully decoupled, **the Agent runtime focuses on finishing the current task, while the memory system organizes past information into queryable reference material**. The two runtimes communicate only through persisted session events and memory APIs, managing their own processes, storage, model clients, and restart lifecycles independently.

| Interaction | Target Behavior |
|---|---|
| **Agent supplies memory material** | Verified human originals, open-ended answers, and turn completion records are persisted first; memory reads them asynchronously from its own cursor. Session ID, turn, and source ID handle verification and deduplication across restarts. |
| **Agent uses memory automatically** | Static rules and cached user profile are available locally in 0ms. Per-turn retrieval starts early in parallel at request entry, races against a short budget before request assembly, and returns an explicit 5-state status (`hit` / `empty` / `skipped` / `timeout` / `unavailable`). The context sent for a turn stays frozen as a snapshot; later turns see newly updated memory. |
| **Agent queries or writes explicitly** | Explicit tool calls (`memory_recall` / `memory_read` / `memory_node_search` / `memory_remember`) and user management actions run within their own budgets and return explicit statuses on failure or offline state so the Agent can proceed or ask the user to confirm. |
| **Memory background consolidation** | Daily notes, Dream, and indexing are scheduled by the memory plugin's private `memory-worker`, reusing DSH's `ctx.llm` as the single system-wide LLM gateway, with serial execution, 429/5xx backoff, and soft foreground yielding to govern shared provider quotas. |

### Three Remaining Coupling Points After PR #175

PR #175 already removed synchronous send fences, host erasure cascades, and native session rewrites. Only three direct couplings remain:

1. **Automatic retrieval still blocks `agent/pre-step` via a synchronous `await`**, bundling static rules, user profile, and dynamic file retrieval into one cross-process RPC.
2. **Hosting `memory-worker` under the Viva main process creates a dual-child relay and splits Viva (`fromViva`) from standalone DSH**, resulting in three-process Note / Dream round-trips (`memory-worker ↔ Viva backend ↔ DSH`).
3. **Ingestion still races across two channels**: the DSH plugin scans session logs for `receiveSource`, while Viva's backend sends `sourceAlias` and `acceptQuestionAnswer` over a separate fire-and-forget IPC channel.

The following sections break the work into four independently deliverable phases.

## 2. Phase 1: Automatic Memory Injection Refactor (3-Layer Split + Early Short-Budget Race + 5-State Protocol)

### 2.1 Timing Budget and Current Bottlenecks

- Local Agent request assembly (`preStep` → `assemble` → `buildRequest`) typically takes **5–20ms**.
- Cross-process IPC + SQLite FTS5 + Markdown verification takes **20–60ms**; adding the ONNX embedding child process (`memory-embedder-worker`) takes **40–150ms** warm and often **>200ms** cold.
- Starting retrieval inside `agent/pre-step` with a 0ms wait means the first turn will almost never catch the result, causing missed implicit conventions (e.g., "send weekly reports to B from now on") or forcing an extra tool round-trip.
- Bundling `MEMORY_RULES`, user `profile`, and dynamic retrieval hits in one `systemPrompt.context('viva-memory')` also duplicates static rules and profile into conversation history on every turn whenever hits change, wasting tokens and hurting prompt-cache stability.

### 2.2 Three-Layer Split

| Layer | Content | Change Frequency | Delivery | Latency |
|---|---|---|---|---|
| **L1 · Static rules** | `MEMORY_RULES` (tool usage, non-instruction rule, timeout/offline guidance) | Static | Registered by [adapter.ts](../plugins/memory/lib/adapter.ts) as a static header `systemPrompt.section` | **0ms** (full KV-cache hit) |
| **L2 · User profile snapshot** | Resident user profile summary body + today's date | Very low (profile change or day rollover) | Pushed by memory worker on `ready` and profile updates as a schema-agnostic text snapshot `{ epoch, revision, text }` and cached in the host; replayed directly on DSH `attach`, combined locally with today's date, and rendered as the sole `systemPrompt.context('viva-profile')` (date-only or empty when `text` is empty or before cold-start worker readiness) | **0ms** (survives independent worker or DSH restarts and search timeouts; swapping the profile backing store later requires zero L2 protocol changes) |
| **L3 · Per-turn retrieval** | 1–3 relevant `daily/digest` snippets or status hint for the current turn | Per turn | Started early when building the final validated delivery + raced against a tight remaining budget; appended in `agent/pre-step` via `decision.messages` as an attributed `source: { kind: 'viva-memory' }` message (`<memory-recall turn="N" ref="<requestId\|messageId>">`), outside `systemPrompt.context` | **Bounded (candidate 120–150ms, tuned via dual-metric benchmark)** |

### 2.3 Early Kickoff, Delivery Binding, and Fast/Slow Path Separation

1. **Early kickoff, exact binding, and task header propagation in Viva desktop**: start prefetch in [acp-bridge.ts](../src/backend/acp-bridge.ts) right when constructing the final validated request—covering foreground `prompt`, `agent:steer`, and scheduled/background task `preparePrompt` / `steerTask`. Once `requestId`, target `sessionId`, and host-verified query text are known, kick off an asynchronous worker search and record `(requestId, sessionId, deadlineAt, ownerEpoch, revision)` **without waiting for `sourceAlias`**, overlapping ACP transport, inbox queueing, `tools.resolve`, and `systemPrompt.assemble`.
   - **Carrying task `requestId` while preserving verbatim task text**: task sessions stay separate from `viva-routing`'s main-session `【请求 ID：】` ledger by wrapping `preparePrompt` / `steerTask` with a lightweight, routing-independent task reference header (reusing the zero-width escaping and `spans` computation from `src/shared/request-routing/header.ts` to produce `{ requestId, wireText, spans }`). `acp-bridge.ts` passes the clean `text`, `wireText`, and `wireSpans: spans` to `recordSource` (so memory intake restores the verbatim headerless task text via `spans`) while registering the host prefetch under `(requestId, sessionId)`. DSH `pre-step` parses `requestId` from the message and claims strictly on `(requestId, sessionId)`—never matching by text content and discarding late results from rebound sessions.
2. **Feed continuation, no-query, and credential-skip boundary (`skipped` status)**: during Feed validation, explicitly extract the user's addition and pass it down as `sourceText` (explicit empty string `''` for a pure draft, never `undefined`). Host prefetch and standalone DSH fallback share the same admission gate: run automatic retrieval only when the effective user text (`sourceText !== undefined ? sourceText : text`) is non-empty and does not match `looksSecret(question)`. For pure drafts, image-only prompts, or credential-bearing inputs, skip retrieval and record a claimable `{ status: 'skipped' }` terminal entry (remaining silent even on late claim, never calling retrieval or appending L3, and separating unexecuted lookups from completed zero-hit `empty` searches in metrics).
3. **Claim precedence: valid completed terminal result before deadline (no dropped hits and no double budget)**:
   - **Step 1 (prefer valid completed terminal result)**: if `(requestId, sessionId)` already has a **still-valid terminal result completed within budget** (`hit` / `empty` / `skipped` / `unavailable`), **consume it immediately in 0ms even if claimed after `deadlineAt`**, with no extra wait and no second search;
   - **Step 2 (apply `deadlineAt` only when unfinished)**: if still pending and before `deadlineAt`, wait only until `deadlineAt` (aborting the worker search and recording `{ status: 'timeout' }` on expiry); if `deadlineAt` has elapsed or `{ status: 'timeout' }` is recorded (retained until claimed or TTL-evicted, e.g., 60s), **consume `timeout` immediately in 0ms with zero second lookup**;
   - **Step 3 (fallback only when genuinely unprefetched)**: only verified inputs that had **no prefetch** (rebound queued prompts, multi-source replays, standalone DSH) fall back to short-budget live retrieval in [adapter.ts](../plugins/memory/lib/adapter.ts) under the same 5-state contract.
4. **Invalidation of unclaimed hits on memory changes (write-back + claim checks, zero extra I/O)**: every prefetch binds `{ ownerEpoch, revision }` at start and in its reply. When the host observes `memory_owner_change` (file edit, disable, enable, forget, Dream commit) advancing `revision`, or `unavailable`, invalidation covers both cached hits and **any in-flight `pending` lookup whose reply arrives later**:
   - Check `result.ownerEpoch === currentEpoch && result.revision === currentRevision` both **when storing a reply** and **when claiming in `pre-step`**; any mismatch immediately marks the result stale so an old reply is never cached or adopted as a valid `hit`;
   - If invalidated before `pre-step` adoption and the original `deadlineAt` still has remaining budget, run one retry within that remaining budget (applying the exact same write-back and claim checks to the retry); if stale again or out of budget, proceed immediately with `timeout`—preventing disabled/deleted content from entering a model request for the first time without adding foreground wait.
5. **Tighter vector cap inside retrieval**: in [memory-file-retrieval.ts](../src/memory/core/memory-file-retrieval.ts), give ONNX vector inference a tighter dedicated cap for automatic searches (e.g., `50–60ms`, skipping cold-start inference while warming in the background) so lexical hits reliably make the first-turn cutoff.

### 2.4 Explicit Automatic Recall Contract

Replace `string | null` with a structured `AutomaticRecallResult`:

```ts
export type AutomaticRecallResult =
  | { status: 'hit', text: string, partial: boolean, hits: Array<{ text: string, names: string[] }> }
  | { status: 'empty' }
  | { status: 'skipped' }
  | { status: 'timeout' }
  | { status: 'unavailable' }
```

- **Zero-hit completeness rule**: return `empty` only when lexical, vector (when enabled), and file verification all finish cleanly with zero hits. When lexical finds zero hits but vector inference, embeddings, or file verification time out or degrade (`partial: true`), **map directly to `timeout`** so callers and the model distinguish an incomplete search from a completed zero-hit search. Requests with no eligible query text (pure draft / image-only) or matching `looksSecret(question)` produce `skipped` and are tracked separately from `empty` and hit-rate denominators.

| Status | Runtime / Diagnostics | Per-Turn Model Message (L3) | Expected Model Behavior |
|---|---|---|---|
| `hit` | Record hit count, latency, and `partial` flag; report `memory_context` once when committed | Append `<memory-recall turn="N" ref="<id>">` snippets; if `partial === true`, add a brief note that automatic search was partial | Use directly; call `memory_recall` if uncertain |
| `empty` | Record completed zero-hit lookup and latency | **Append nothing** (zero noise) | Answer normally without redundant recall |
| `skipped` | Record unexecuted lookup (pure draft / image-only / `looksSecret` match), tracked separately from `empty` | **Append nothing** (zero noise) | Answer normally |
| `timeout` | Track timeout rate and fallback event | Append `<memory-recall turn="N" ref="<id>">`: automatic memory lookup timed out or was incomplete; call `memory_recall` if the task depends on prior conventions | Ignore for unrelated prompts; **call `memory_recall`** (wider tool budget) when prior preferences/recipients matter |
| `unavailable` | Record offline count | Append `<memory-recall turn="N" ref="<id>">`: memory service is currently unavailable | **Skip doomed `memory_recall` calls**; ask the user directly if critical info is missing |

### 2.5 Context Injection, Cross-Turn Policy, and Event Reporting Invariants

- **Physical isolation between L3 and L2**: L2 owns `systemPrompt.context('viva-profile')` exclusively; L3 stays out of `systemPrompt.context` and is appended via `decision.messages` (`source: { kind: 'viva-memory' }`) in `agent/pre-step`. Changes in L3 never trigger DSH's `RuntimeContextProjection` to re-emit the full profile or append a clearing reminder.
- **Keep historical L3 nodes across turns to preserve KV cache (Option A)**: L3 messages carry `<memory-recall turn="N" ref="<requestId|messageId>">` and state that they apply only as automatic recall reference for the referenced message, not latest state for later turns. Subsequent turns **never rewrite or replace prior `viva-memory` nodes**, keeping cross-turn prompt-cache prefixes intact; an `empty` or `skipped` next turn appends nothing.
- **Freezing begins upon snapshot adoption; parallelize multi-interjection steps under one deadline**:
  - Unclaimed prefetches remain subject to memory-change invalidation (§2.3 item 4);
  - Once Step 1 adopts L3, ordinary tool continuations (`humanMessages(decision.messages).length === 0`) are **strictly frozen**—keeping Step 1's L3 with no re-query and no deletion;
  - Mid-turn user interjections (`agent:steer`, `humanMessages(decision.messages).length > 0`): run retrieval for the new user prompt and append a new `viva-memory` message without modifying L2 or prior steps;
  - When a single step claims multiple pending interjections (`[A, B]`) from the inbox, claim/query them **in parallel under one shared step absolute deadline** (never multiplying budgets), attribute each L3 message via `ref="<requestId|messageId>"`, and append them in deterministic original order `[A, B]` even if B resolves first.
- **Commit-confirmed `memory_context` events**:
  - Remove eager `injected` emission from worker-side `fileContext()`, and do not emit before `agent/pre-step` returns (DSH still runs `prepareRequest` and re-checks cancellation afterward);
  - In `agent/pre-step`, stage pending injection metadata keyed by the L3 `UserMessage`'s unique `message.id`;
  - On `session/event` observing that exact `user/message` (`source.kind === 'viva-memory'`) **actually committed to the session** (strictly after `prepareRequest` and abort checks, immediately before `buildRequest`), claim and delete the staged entry (exact-once dedup by `message.id`) and emit `memory_context`; prune any uncommitted entries on `turn/end` and `session/disposed`. Note: this event confirms that memory entered the session, while first-request evidence coverage metrics are still measured from **actual emitted model requests**.

## 3. Phase 2: Retire Manual Profile and Switch Directly to Auto-Maintained Resident Profile

### 3.1 Rationale and Strategy

Today's L2 profile relies on users manually filling `role`, `projects`, and `preferences` during onboarding (`saveIntro`) or in About You. Starting from blank forms creates friction and quickly goes stale while splitting the mental model into a manual `profile` table and Dream-maintained `digest` files.

There are no existing users. Acceptance for Phases 1 and 2 starts from a fresh install, with no compatibility requirement for earlier databases, IPC contracts or pending operations from older versions. Phase 1’s L2 snapshot `{ epoch, revision, text }` is independent of profile fields, so Phase 2 can switch the source and remove the manual profile table, IPC and UI in one PR.

### 3.2 Single-Step Switch Scope

1. **Memory side (swap L2 content source with zero L2 transport or DSH adapter changes)**
   - **Unique global profile identity, source isolation, and L3 exclusion**: pin the resident profile to the single identity **`(USER_WORKSPACE, 'digest/personal/profile.md')`**, where `USER_WORKSPACE = memoryHash(JSON.stringify([{ kind: 'user' }, { kind: 'user' }, null]))`. Keep its L2 budget tightly bounded under one shared constant (e.g., `MAX_PROFILE_L2_CHARS = 800`, counted by Unicode code points `[...text].length`) to cross-task role context, durable preferences, and communication/output style; project-specific details and conventions stay in regular files recalled via L3.
     - **Dedicated lightweight profile pass, unified `pendingBatch` checkpoint, and commit isolation**:
       - **Ordinary Dream `consolidate` (case-insensitive read-only profile target, post-filter `hasMore` recalculation, and oversized handoff)**: define a single cross-platform helper **`isReservedProfilePath(path) => path.toLowerCase() === 'digest/personal/profile.md'`** (with the canonical write path fixed to lowercase `'digest/personal/profile.md'`). Explicitly instruct the ordinary planner that this reserved path is read-only (never `CREATE` or `REFINE`), and exclude matches of `isReservedProfilePath` from `existingDigests` catalog and `node_search` target candidates. During plan validation **before persisting `pendingBatch`**, strip every operation matching `isReservedProfilePath(op.path)` (including case variants like `digest/personal/Profile.md`) along with any subsequent operation in the same plan that depends on a stripped draft, preserving independent ordinary file operations so they commit once without retry loops, and recompute **`effectiveHasMore = plan.hasMore && retainedOperations.length > 0`** after filtering (when zero operations survive, apply baseline empty-plan semantics with `effectiveHasMore = false` so the eligible profile pass runs and advances the checkpoint; when valid ordinary operations survive and the model set `hasMore: true`, keep `effectiveHasMore = true` for multi-pass batching). The commit guard likewise enforces `isReservedProfilePath` as defense-in-depth, rejecting writes from ordinary `consolidate`, any non-`USER_WORKSPACE`, or any non-canonical casing variant (such as `Profile.md`) so ordinary digests can never occupy the path on case-insensitive volumes. When a single note triggers `context-window-exceeded` during ordinary `consolidate` (with `inputsCurrent()` true), keep recording `oversizedAny = true` and the `oversized` diagnostic (preserving the `size-limit` outcome), but **do not call `notes.markProcessed` and return early**—instead treat the ordinary pass as `operations: []` with `checkpointRefs = fileRefs` and flow directly into the dedicated profile pass and shared checkpoint path (if the profile pass itself hits single-note `context-window-exceeded`, record its diagnostic and advance the checkpoint without looping). Full daily-note batch Markdown and `read` stay unchanged so ordinary `digest/*` files continue using all eligible material (including pre-deletion sources) normally.

2. Verify disable/delete separately: ① a new session's first model request contains no profile body; ② in an existing session, the latest L2 snapshot is cleared and later steps never re-inject the old profile body (without rewriting earlier history messages);

5. ② starting after both the digest and resident profile have receipts, verify disk-unverifiable recovery and manual completion—(a) temporarily move the note Markdown file aside, run checkpoint verification once, then restore the same file: recovery finishes only that revision's checkpoint with zero extra model calls or file revisions; ## 4. Phase 3 (Consolidated): Return Memory Worker Ownership to the DSH Plugin, Unify on One Path, and Add Quota Governance

### 4.1 Decision and Process Consolidation

After architectural review, both product premises behind a DSH-independent LLM client are confirmed to be **No**:
1. The "About You" memory management UI does **not** need to operate independently of DSH during the 1–2 second window when no model is configured, DSH crashes, or DSH restarts on a model switch;
2. There is no near-term plan to support non-DSH Agent runtimes or to run background memory consolidation while DSH is shut down.

Therefore, **the original Phase 3 plan (building a second LLM client and credential-sync IPC inside `memory-worker`) is cancelled**, and process ownership returns to the **`viva-memory` DSH plugin (supervising its own private `memory-worker` child process)**:

- **Single-tree process topology**: `Viva main process → DSH process → viva-memory plugin → private memory-worker child process`. Viva supervises only DSH; Note / Dream `ctx.llm` compute callbacks run directly between the plugin and its private worker without three-hop relaying through the Viva main process.
- **Single LLM gateway invariant**: DSH (`ctx.llm`) remains the sole owner of provider wire protocols, DeepSeek account token refresh (`llm-deepseek-account`), proxy handling, retries, and credentials, avoiding duplicated transport plumbing and wider plaintext API-key exposure.
- **Concrete deletion list (eliminating dual-mode maintenance tax)**:
  - Delete `src/backend/desktop-memory-owner.ts` (Viva-side supervisor and bidirectional relay);
  - Delete `src/backend/memory-prefetch.ts` (Viva-hosted cross-process prefetch coordinator);
  - Delete `fromViva()` in `plugins/memory/lib/standalone-owner.ts` and remove `claimPrefetch` / `refreshPrefetch` / `claimPrefetchBatch` / `reconciled` from `MemoryOwnerConnection`, converging Viva desktop and standalone DSH 100% onto `standaloneOwner`;
  - Remove `memoryOwnerPrefetchCancelled` and host-prefetch-only `prefetchRecall` from `src/memory/contracts/host.ts`, and remove `bindDsh` / `startPrefetch` / `cancelPrefetch` / `finishPrefetch` / `clearSessionPrefetches` calls from `src/backend/acp-bridge.ts`.
- **Keep process-level isolation**: the `viva-memory` plugin continues to supervise a dedicated `memory-worker` child process that owns SQLite, Markdown verification, FTS5, and ONNX embeddings so synchronous database I/O and embedding work never block the DSH main thread.
- **Retain Phases 1 and 2 core behavior**: L1 static rules, L2 local profile cache, L3 `decision.messages` anchoring with the 5-state recall protocol, fast/slow vector separation, and the full Phase 2 resident-profile + Dream checkpoint recovery logic stay intact.

### 4.2 Parent-Process Management IPC, Lightweight Transitional Ingestion Proxy, and Trust Boundary

1. **Dedicated parent-process management channel (exact `remote-memory-channel.ts` wire contract)**:
   - Viva's main process sends `memory_host_request` frames over the existing parent-child IPC link (extending the `send` branch in [remote-memory-channel.ts](../src/backend/remote-memory-channel.ts) so the first hop carries `protocol: MEMORY_HOST_PROTOCOL`, `requestId`, `epoch`, `method`, `input`, plus optional `read: { readBatchId, budgetMs }`, `deadlineAt`, and `diagnostics`);
   - **First-hop explicit cancellation propagation**: if a caller's `AbortSignal` aborts **before** its budget expires (e.g., user cancels an in-flight `readBatch`), `remote-memory-channel.ts` emits `{ type: 'memory_host_cancel', protocol: MEMORY_HOST_PROTOCOL, requestId, epoch }` while **keeping the `executions` read slot occupied until the terminal `memory_host_result` (or `processExited()`) arrives**;
   - When `config.host === true` and `port.send` is present, `viva-memory` validates `protocol === MEMORY_HOST_PROTOCOL`, `epoch === owner.epoch`, and the `HostMemoryMethod` allowlist, binds a per-`requestId` `AbortController` (aborted on `memory_host_cancel`), relays to its private `memory-worker`, and replies with **`memory_host_result`** (success: `{ type: 'memory_host_result', protocol, requestId, epoch, ok: true, result }`; error: `{ type: 'memory_host_result', protocol, requestId, epoch, ok: false, error }` using existing **`memoryHostFailure`** in [domain-error.ts](../src/memory/contracts/domain-error.ts) to preserve `code`, `reason`, `domainCode`, and `domainDetails`);
   - **Carry execution options across both hops**: extend `MemoryOwnerConnection.callHost` and [standalone-owner.ts](../plugins/memory/lib/standalone-owner.ts) to forward `OwnerCallOptions` (`signal`, `budgetMs`, `waitForCompletion`, `deadlineAt`) verbatim to `supervisor.callHost`:
     - Requests carrying `read` (`readBatch`) invoke `{ signal, budgetMs: read.budgetMs, waitForCompletion: true }` so caller cancellation reaches the worker while the plugin still awaits terminal worker completion before emitting `memory_host_result` and releasing the slot;
     - Requests carrying `deadlineAt` forward the remaining `budgetMs`, `deadlineAt`, and `signal` through to the worker;
   - The plugin forwards `memory_owner_state` (including `profileDeletionGen`), `memory_owner_change`, and `memory_owner_context_used` events from its private `memory-worker` over parent IPC to Viva's main process for UI refresh, diagnostics, and `question-desk` `questionProfileGen` snapshots;
   - **Retiring DSH connection fencing**: Viva binds each DSH child process to a monotonic lifetime guard (`DshLifetime`); on DSH exit or replacement, Viva immediately calls `channel.processExited()` and drops any late IPC frames from the retiring DSH child.
2. **Lightweight transitional ingestion proxy (bridging PR 3 → PR 4A without throwaway tables or temporary frames)**:
   - Until Phase 4 removes `sourceAlias` / `acceptQuestionAnswer`, `hostNamespace: 'viva'` continues forwarding the full `HostMemoryMethod` allowlist (managed-file CRUD, Dream commands, idempotent `getOperation`, and `sourceAlias` / `acceptQuestionAnswer`) over parent IPC;
   - [compose.ts](../src/backend/compose.ts) replaces silent drops during `recovering` (`if (memoryOffline()) return`) with a bounded pending intake queue keyed by stable `operationId` (recording explicit diagnostics on overflow) that replays unacknowledged entries idempotently when `memory_owner_state` transitions to `ready`; `acceptQuestionAnswer` awaits a bounded acknowledgement before completing delivery to DSH;
   - [owner.ts](../src/memory/node/owner.ts) retains existing `(session, wire_hash)` `sourceAlias` matching, ensuring `origin === 'derived'` is never promoted to `'original'` and cancelled turns never emit a Daily Note; because Phase 4 immediately removes `sourceAlias`, Phase 3 deliberately avoids adding throwaway transitional tables (`owner_turn_receipts`) or temporary cross-process frames (`memory_query_handoff`).
3. **Permission boundary and explicit trust model**:
   - Only the parent-process IPC channel may invoke `callHost`; model tools can only invoke the minimal `sidecarRequest` allowlist (**`remember`, `recall`, `file_read`, `node_search`**—preserving authorized reads while keeping all management methods off the model-tool path); Viva's main process never opens `memory.db` directly, preserving single-owner locking via `owner-lock.ts`;
   - **Explicit trust assumption for user-installed DSH plugins**: Viva allows users to install and enable third-party DSH plugins via [plugins-ipc.ts](../src/backend/plugins-ipc.ts). Because DSH and its plugins execute in the same Node.js process, enabling a third-party plugin grants it full in-process trust equivalent to DSH itself; the `callHost` / `sidecarRequest` boundary enforces least privilege on the model-tool and host protocol surfaces, not OS-level sandboxing against untrusted in-process plugins.
4. **Availability semantics**:
   - While DSH is not running, crashing, or restarting on a model switch, Viva's main process calls `channel.processExited()` and reports `unavailable` (UI shows a transient connecting/unavailable state), recovering automatically once DSH reports `memory_owner_state (ready)`;
   - Legacy `#161` unit and smoke tests asserting management availability while DSH is stopped are updated to match this semantics, while retaining the worker-only crash recovery guarantee (DSH stays alive, replaces the crashed worker, and keeps the root lock intact).

### 4.3 Single-Hop DSH L3 Retrieval and Restart/Crash L2 Rebuild

1. **Single-hop short-budget L3 retrieval with worker-side version bracket checks**:
   - After deleting the Viva-hosted prefetch bridge, `viva-memory` initiates L3 automatic recall directly inside `agent/pre-step` concurrently for every admitted human message produced by the unified human-message extractor (`humanMessages` in Phase 3, upgraded to `extractHumanMessages` in Phase 4):
     - All messages in the step share a single absolute deadline `stepDeadlineAt = Date.now() + DAILY_MEMORY_DEFAULTS.automaticContextBudgetMs` (default `150ms`) over a **single-hop local IPC** call (`owner.call('automaticRecall', ...)`) from the plugin to its private `memory-worker`;
     - Starting at `agent/pre-step` eliminates orphan pre-dispatch prefetches and cancellation races, while keeping `looksSecret` / empty skipping, 55ms fast/slow vector caps, and resident-profile L3 slot exclusion;
     - **Authoritative worker-side version check & single-layer at-most-once refresh**: move the database-level `(startRevision, endRevision)` bracket check from deleted `prefetchRecall` into `owner-worker.ts` `automaticRecall`—reading `startRevision = store.revision()` before search and `endRevision = store.revision()` after search and returning `{ epoch, revision: endRevision, stale: result.status === 'hit' && startRevision !== endRevision, result }`; if `adapter.ts` observes `stale === true` or `(item.epoch !== owner.epoch || item.revision < (currentRevision ?? 0))`, it performs **at most one re-query** within the remaining `stepDeadlineAt` budget and injects `<memory-recall>` in original message order only for hits satisfying `!item.stale && item.epoch === owner.epoch && item.revision >= (currentRevision ?? 0) && !signal.aborted`;
     - **Zero phantom receipts**: emit `reportContextUsed` only after `session/event: user/message (viva-memory)` is appended to the session (`prepareCall` failure or cancellation never emits a phantom receipt).
   - **Cold/warm benchmark calibration**: update [benchmark-memory-latency.ts](../scripts/benchmark-memory-latency.ts) to remove `desktop-memory-owner` imports and prefetch-frame interception, running directly against `standaloneOwner` plus a working bypass baseline to compare cold/warm first emitted model request P95 latency and evidence hit rate against `5e96068`.
2. **L2 cache rebuild after DSH restart or worker-only crash (epoch-safe three-step boot & late-subscriber replay)**:
   - Because `owner-supervisor.ts` establishes `instance.epoch` from a state frame and `adapter.ts` filters profiles by `owner.epoch`, after `recover()` `owner-worker.ts` emits frames in strict three-step order:
     1. **`memory_owner_state { state: 'recovering', epoch: newEpoch, ... }`** first (establishing `newEpoch` and clearing any old-epoch `cachedProfile`);
     2. **`memory_owner_profile { epoch: newEpoch, revision, text, profileDeletionGen }`** second (accepted and cached by both supervisor and adapter);
     3. **`memory_owner_state { state: 'ready', epoch: newEpoch, ... }`** third (so L2 is already populated the instant `ready` becomes true, with zero gap);
   - **Ordered replay for late subscribers**: in `subscribe(listener)` of [standalone-owner.ts](../plugins/memory/lib/standalone-owner.ts) and [owner-supervisor.ts](../src/memory/node/owner-supervisor.ts), when `snapshot.state === 'ready'` and a cached `profileSnapshot` exists for the same epoch, replay in the identical three-step order so a late-attaching `adapter.ts` sees the populated L2 profile inside its first `ready` callback;
   - **Fail-closed cache invalidation**: on either a DSH restart or a worker-only crash (supervisor emits `unavailable`), `adapter.ts` immediately clears `cachedProfile` (`currentProfileText()` returns text only when `owner.ready() && cachedProfile?.epoch === owner.epoch`, otherwise `''`);
   - The plugin monotonically updates `cachedProfile` per `(epoch, revision)` (accepting `text: ''` as a valid clear) for 0ms synchronous reads by `systemPrompt.context('viva-profile')`.

### 4.4 Quota Governance & Scheduler Contracts (429/5xx `Retry-After` and Lightweight Soft Foreground Yielding)

1. **Hard concurrency cap = 1**: Note and Dream remain serialized through the existing single-loop `effects` queue in `memory-worker`.
2. **429 / 5xx classification and end-to-end `Retry-After` propagation (no extra SQLite cooldown table)**:
   - **Boundary 1 — Plugin classifier ([model.ts](../plugins/memory/lib/model.ts))**: extend `memoryProviderFailure(input)` to handle BOTH DSH terminal error finish frames (read via **`assembler.finish.failure`**) AND thrown errors (`LlmError.failure` or top-level `{ code, status, providerRetryAfterMs }`):
     - `code === 'RATE_LIMIT'` or `status === 429` → `new MemoryComputeError('rate-limited', { retryAfterMs })`;
     - `code === 'SERVER'` / `TRANSPORT` / `STREAM_CLOSED` or `500 <= status <= 599` → `new MemoryComputeError('provider-overloaded', { retryAfterMs })`;
     - Validate `retryAfterMs` as a positive integer capped at `MAX_RETRY_AFTER_MS = 3_600_000` ms to prevent malformed headers from stalling the queue indefinitely.
   - **Boundary 2 — Plugin `compute` catch ([adapter.ts](../plugins/memory/lib/adapter.ts))**: pass the full caught error (preserving `LlmError.failure`) into `memoryProviderFailure(error)`.
   - **Boundary 3 — Cross-process contract & worker reconstruction ([memory-contract.ts](../src/memory/contracts/memory-contract.ts), [compute.ts](../src/memory/contracts/compute.ts), [owner-rpc.ts](../src/memory/contracts/owner-rpc.ts), [owner-rpc-peer.ts](../src/memory/node/owner-rpc-peer.ts), [owner-worker.ts](../src/memory/node/owner-worker.ts))**:
     - Extend `memoryComputeFailure` with `'rate-limited' | 'provider-overloaded' | 'deferred'`;
     - Add optional `readonly retryAfterMs?: number` to `MemoryComputeError`;
     - Carry optional positive-integer `retryAfterMs` on RPC `Failure` frames and reconstruct `new MemoryComputeError(reason, { retryAfterMs })` inside `owner-worker.ts`.
   - **Boundary 4 — Note and Dream propagation ([memory-note-jobs.ts](../src/memory/core/memory-note-jobs.ts) & [memory-dream-jobs.ts](../src/memory/core/memory-dream-jobs.ts))**:
     - Map caught `MemoryComputeError` to `{ kind: 'defer', delayMs: error.retryAfterMs ?? 3_000 }` for `'deferred'`, `{ kind: 'retry', delayMs: error.retryAfterMs, cooldown: true }` when `retryAfterMs` is set, and plain `'retry'` otherwise (using registered exponential backoff starting at `1_000ms`);
     - `memory-dream-jobs.ts` (covering both main consolidation and profile planning passes) carries a structured retry/defer result preserving the maximum `retryAfterMs` or `defer`.
   - **Boundary 5 — `effects` scheduling ([ports/effects.ts](../src/memory/core/ports/effects.ts) & [node/effects.ts](../src/memory/node/effects.ts))**:
     - Extend `Outcome` to `'done' | 'wait' | 'retry' | { kind: 'retry', delayMs: number, cooldown?: boolean } | { kind: 'defer', delayMs: number }`;
     - Add a single integer column `cooldown_until` (default `0`) on the existing `effects` table (**without adding a new table or changing `effects` queries to `LEFT JOIN`**): `{ kind: 'retry', delayMs, cooldown: true }` binds `:deadline = now() + delayMs` once and atomically executes `cooldown_until = MAX(cooldown_until, :deadline)`, `due_at = MAX(due_at, cooldown_until, :deadline)` (explicitly including `:deadline` in `due_at` because a single SQLite `UPDATE` reads the old `cooldown_until` on the RHS), and increments `attempts`; `effects.queue()`'s `ON CONFLICT DO UPDATE` preserves `effects.cooldown_until` and enforces `due_at = MAX(excluded.due_at, effects.cooldown_until)`, so manual Dream or managed-file edits (even **immediately after restart**) never erase an outstanding provider 429 deadline, while a 3s foreground soft deferral leaves `cooldown_until` untouched and is immediately overridden by manual Dream;
     - `{ kind: 'defer', delayMs }` persists `due_at = now() + delayMs` (leaving `cooldown_until` untouched and **without incrementing `attempts`**), yielding the current `effects` pass so unrelated effects run immediately.
3. **Lightweight soft foreground yielding**:
   - **Foreground activity tracking ([adapter.ts](../plugins/memory/lib/adapter.ts))**: intercept `ctx.on('llm/stream', ...)` (using `isAgentLoopRequest(options)` to exclude `memorySource`-originated calls) and maintain an `activeForegroundStreams` counter released in `finally`;
   - **Simple in-memory anti-starvation state**: add optional `manual?: boolean` to `MemoryCompute` (set to `true` by `memory-dream-jobs.ts` when `MANUAL_JOB` is active). When `activeForegroundStreams > 0 && job.manual !== true`:
     - Track a single in-memory `firstDeferredAt` window: while elapsed `< MAX_SOFT_YIELD_MS` (`30_000` ms), throw `new MemoryComputeError('deferred', { retryAfterMs: 3_000 })`;
     - Once 30s elapses, mark the current background batch exempt until foreground activity clears or `owner.epoch` changes, ensuring both consolidation and profile planning passes complete and persist their checkpoint;
   - **Never abort in-flight work**: background requests already streaming are never aborted when a foreground turn begins;
   - **Manual Dream exemption**: `job.manual === true` bypasses foreground soft yielding (while still respecting active provider cooldown floors).
4. **Background light-model hook**: `MemoryCompute` continues to carry `{ provider, model }`, allowing future background stages to target a lighter configured model in DSH.

## 5. Phase 4 (Consolidated): DSH Persisted Session Log as Single Source of Truth and Background-Task Memory Integration

### 5.1 Root Cause & Decoupling Boundaries

With memory hosted inside the `viva-memory` DSH plugin, memory should neither couple to Viva's private `history.db` tables nor reach back into unrelated plugins (`history`, `tasks`, `fork`, `routing`, `compaction`) or `acp-bridge.ts`'s core turn state machine. Three tightly coupled ingestion defects remain to be eliminated:

1. **Dual-channel async races**: the DSH plugin scans sessions (`receiveSource`) while Viva's backend fires async `sourceAlias` and `acceptQuestionAnswer`, so a late `acceptQuestionAnswer` can be dropped by `owner_turns` and a late `sourceAlias` waits for `turn/end` replay.
2. **Duplicate conversation history files**: `memory-note-store.ts` writes a second copy of conversation turns into `session/dialog/<hash>.jsonl`, duplicating DSH's native `<dshHome>/sessions` persisted log.
3. **Background task sessions missing from memory**: [acp-bridge.ts](../src/backend/acp-bridge.ts) calls `recordSource` in `preparePrompt`/`steer` without a `sourceId`, causing [compose.ts](../src/backend/compose.ts) to mark them `origin: 'derived'` so `owner.ts` drops both the message and the turn's assistant reply; `viva-report` back to the main thread is also skipped; and background question answers are isolated under `{ kind: 'task', id: session }`, leaving background-task instructions, steers, and conclusions unrecallable from the main conversation.

To keep PR scope manageable and independently verifiable, Phase 4 splits cleanly into **PR 4A (Single Source of Truth + Background-Task Provenance & `humanSpans`)** and **PR 4B (Native `ask_user_question` Ingestion)**.

### 5.2 Persisted Read-Handle Durability, CAS Cursors, Read-Only Cold Catch-Up, and Fresh Schema Contract (PR 4A)

1. **`flush() + open('read')` verified durable slice as the single persistence boundary**:
   - In the pinned DSH JSONL backend, `ctx.sessions.flush(session)` returns `true` even on a session with no persistence write handle (where `open(id, 'read')` then throws `SessionPersistenceNotFoundError`);
   - Therefore, define one shared helper **`readVerifiedDurableSlice(ctx, session, fromSeq, endSeq)`** in [ingestion.ts](../plugins/memory/lib/ingestion.ts): await `ctx.sessions.flush(session) === true`, open a short-lived read handle `ctx.sessionPersistence.open(session.id, 'read')` (closed in `finally`), and **read the actual persisted `[fromSeq, endSeq)` events directly from disk** (failing closed on `flush` returning `false`/throwing, `SessionPersistenceNotFoundError`, or fewer than `endSeq - fromSeq` events);
   - Both regular turn ingestion and mid-turn `memory_remember` staging consume ONLY events returned by `readVerifiedDurableSlice` (never unverified `session.snapshotEvents()`), and handle synthetic `turn/end` closers produced by DSH `repair.ts`.
2. **Atomic SQLite CAS cursor & range registration (read-only cold scan—never acquiring write leases)**:
   - Remove all ongoing `session/dialog/<hash>.jsonl` writes from `memory-note-store.ts`;
   - Add two lightweight intake tables in `memory-worker`:
     - `owner_intake_cursors (session PRIMARY KEY, next_seq, inherited_seq, session_kind, conversation, created_at, updated_at)`;
     - `memory_note_ranges (range_id PRIMARY KEY, note_key, session, workspace, day, from_seq, to_seq, turn, sources_json, assistant_digest, assistant_valid, status)`, where `range_id = sha256(session, from_seq, to_seq)` is unique on `(session, from_seq, to_seq)` (allowing multiple batches on the same day to update the same `note_key`);
   - **Gap-free CAS cursor guard & terminal-reason gating (only `completed` turns insert canonical sources, Notes, and task conclusions)**: reading contiguously from `expectedNextSeq`, process closed turns (`turn/start ... turn/end`) or verified non-turn prefixes in one SQLite transaction asserting `cursor.next_seq === expectedNextSeq` (identical `(session, from_seq, to_seq)` returns idempotently; mismatch rejects and rescans from live `next_seq`). On ANY terminal `turn/end`, atomically clear `owner_open_turn_sources` and advance `owner_intake_cursors.next_seq = endSeq` in that transaction, but **ONLY when `turn/end` has `reason.kind === 'completed'` atomically upsert/reuse all filtered canonical `memory_sources` for that turn (including ordinary unstaged prompts and `task-assistant` conclusions) and insert `memory_note_ranges`**—ordinary user cancellation (persisted by pinned DSH as `reason.kind === 'aborted'` with `reason.reason.kind === 'user'`) and physical DSH repair closers (`reason.kind === 'interrupted'`) advance the cursor and clear staging without emitting a Daily Note range or publishing an intermediate assistant message as a globally recallable task conclusion;
   - **Read-only cold scan (never takes `open(id, 'write')`)**: cold catch-up processes only closed turns (`turn/start ... turn/end`); if a previous crash left an unclosed trailing turn without `turn/end`, cold scan leaves the cursor before that unclosed turn until DSH reopens the session and `repair.ts` appends a `reason.kind === 'interrupted'` `turn/end`, after which the terminal-reason gate above safely advances the cursor and clears staging without emitting a partial Note—preventing cold scans from holding a write lease across cross-process SQLite waits and blocking user reopen with `SessionAlreadyOwnedError`;
   - **Crash guarantees**: crashing before `flush` leaves `next_seq` unchanged for replay; crashing after committing the range keeps `memory_note_ranges` queued, and `WRITE_NOTE` commits each batch idempotently via `journal.commit`'s `(note_key, generation)` receipt while marking `range_id` consumed in the same apply transaction.
3. **Zero-intrusion fork prefix cut & retryable cold-session enumeration**:
   - **Keep [plugins/fork/index.ts](../plugins/fork/index.ts) untouched**: continue initializing cursor start from DSH's persisted `session.inheritedEventCount` (`Math.max(inherited, nextSeq)` in [ingestion.ts](../plugins/memory/lib/ingestion.ts)), skipping inherited turns without double-counting; directory switching naturally binds the child session's new `project` scope (no local `<childId>.json` spool or `owner_fork_lineage` table);
   - **Retryable startup enumeration & cold-to-live handoff**: once `memory-worker` reaches `ready`, wrap `ctx.sessionPersistence.list()` in a lifecycle-bound backoff retry loop; scan non-active sessions read-only (`open(id, 'read')`, always closed in `finally`) serialized per `sessionId` against live `session/created` via `ingestion.ts`, retrying transient per-session read errors until success, live open, or confirmed `SessionPersistenceNotFoundError`.
4. **On-demand range reads and missing-session vs. transient-error distinction**:
   - When `WRITE_NOTE` runs (after `noteInterval`, day rollover, or background-task completion flush), `memory-worker` invokes `readSessionRange({ sessionId, fromSeq, toSeq })` using `ctx.sessionPersistence.open(SessionId(sessionId), 'read')` (`finally` `close()`) and filters via `looksSecret`;
   - Catch `SessionPersistenceNotFoundError` from both `open()` and `read()` to clear/skip the pending range (`{ status: 'deleted' }`) only when deletion is confirmed; transient I/O errors or short reads recheck with a fresh handle and return `{ status: 'unavailable' }` so `effects` retries.
5. **Fresh schema contract bump (aligned with §3.1 no-existing-users premise)**:
   - Consistent with §3.1 (no existing users; PR 3 and PR 4 ship in the same rollout window), bump **`MEMORY_CONTRACT`** in [memory-store.ts](../src/memory/node/memory-store.ts) and initialize a clean Phase 4 schema (adding only 4 lightweight tables in total: `owner_intake_cursors`, `memory_note_ranges`, `owner_open_turn_sources`, `owner_question_answers`, plus `source_kind`, `profile_eligible`, and direct answer-question metadata columns `question_valid`, `question_sources_json`, `question_at`, `question_profile_gen` on `memory_sources`);
   - Markdown parsers tolerate and ignore any legacy `source_conversation: [[session/dialog/...]]` frontmatter while new Daily Notes omit it; no locked forward migration, `memory_legacy_deferred_turns`, dual-track `legacyTaskProfileRefs`, or special-case read exemptions are added.

2. **Unified host eligibility decision, pre-receipt privacy filtering, and zero-wait submission ([question-channel.ts](../src/backend/question-channel.ts), [compose.ts](../src/backend/compose.ts))**:
   - `question-channel.ts` keeps display normalization unchanged while retaining raw `header` strings (`rawHeaders`) on the in-memory `Pending` entry so host and DSH evaluate identical >200-char header context;
   - Shared Node-only module [src/memory/node/question-answer-memory.ts](../src/memory/node/question-answer-memory.ts) (inside `src/memory/node/`, bundled automatically with the standalone memory plugin while keeping renderer-imported `src/shared/question-answer.ts` free of `node:crypto`) provides `eligibleQuestionAnswers(cards, answers)`:
     - Validates unique 1:1 card/answer mapping and excludes cards or custom answers containing SQLite-lossy NUL (`\u0000`) or unpaired UTF-16 surrogates (UI still delivers the answer to DSH);
     - Suppresses the entire batch if ANY raw card string field (`card.id`, `question`, `header`, every option's `label` / `description`, including options 9+) hits `looksSecret` or invalid characters;
     - For each non-empty trimmed `custom` answer, in addition to standalone `looksSecret`, strips trailing whitespace and prompt punctuation from `question` / `header` via a **linear O(n) backward scan** and checks contextual `looksSecret(\`${stem}: ${custom}\`)` (blocking split credentials like `"What is your OTP?"` / `"请输入验证码："` / `"Password?"` + secret value); returns only eligible cards canonically sorted by `id` so rejected secrets are never hashed while safe sibling cards survive;

3. **One scalar-only receipt table `owner_question_receipts`, per-session serial ordering, and explicit durability tradeoff**:
   - Replace `owner_answer_sources` in `memory.db` with **`owner_question_receipts (session, turn, call_seq, call_id_hash, conversation_id, answered_at, question_profile_gen, answer_profile_gen, answer_batch_digest, created_at, PRIMARY KEY (session, call_seq, call_id_hash))`** (retaining `owner_active_turns` for `foregroundTurn`, `canCommit`, and `memory_remember` turn guards):
     - `call_id_hash = sha256(callId)` (never raw provider `callId`);
     - `answer_batch_digest = sha256(JSON.stringify(eligible.map(({ id, custom }) => ({ id, custom }))))`, hashed strictly over the pre-filtered eligible `{ id, custom }` projection—never persisting a guessable digest of rejected secrets while rejecting `tools/post-execute` rewrites that alter eligible custom text;
   - `plugins/questions/lib/channel.ts` emits a synchronous local Cordis event before `entry.resolve(answer)` inside `try/catch` + `finally` (a listener throw can never strand `ask()`); `plugins/memory/lib/adapter.ts` (registered ONLY when `config.host === true`) synchronously enqueues `recordQuestionReceipt` onto the session's existing `intake` serial queue (with `.catch(report)`);
   - **Strict ordering guarantees (zero race, zero UI block)**: every live scan entry point in [ingestion.ts](../plugins/memory/lib/ingestion.ts) (`synchronize`, `stageOpenTurn`, and retries) captures `targetEndSeq = Number(session.seq)` **at enqueue time** and passes it to `scanLive` (preventing an earlier queued scan from settling a later `turn/end` ahead of a queued receipt); `scanCold` captures a monotonic per-session `liveEpoch` at entry (before `enqueue`) and rechecks it at closure start, after `intakeCursor`, after `readAllPersistedFrom`, and across CAS retries (discarding stale cold reads even if a session opened and closed mid-read);
   - **Explicit durability tradeoff**: to avoid UI ACK waits, if `memory-worker` crashes or is unavailable before the queued receipt commits to SQLite, replay sees no receipt and fails closed (Q&A is unaffected; any deterministic `source_id` in history is a harmless correlation key);
   - **Safe retirement**: receipts survive `stageOpenTurnSources` (for mid-turn `memory_remember`) and are deleted atomically at ANY terminal `settleTurn` (`completed`, `aborted`, `interrupted`, `error`) via `WHERE session = ? AND (turn <= ? OR call_seq < ?)` (covering lost buffered PTC starts closed at an earlier seq by `repair.ts`); cold catch-up deletes by `session` ONLY on confirmed `SessionPersistenceNotFoundError` (transient read failures retain receipts); a 30-day safety-net TTL runs ONLY after an initial cold catch-up pass completes for long-abandoned unclosed sessions.
4. **Native & PTC deterministic folding, persisted `eventSeq` dependencies, and two-layer deletion watermarks**:
   - Shared folding in [ingestion.ts](../plugins/memory/lib/ingestion.ts) serves `stageOpenTurn`, `settleTurn`, and cold catch-up:
     - Native folding accepts ONLY `tool/result` with `surfaceOp === 'append'` (excluding compaction replacements), `isError !== true`, `error === undefined` (excluding `repair.ts` `TOOL_OUTCOME_UNKNOWN`), and `sourceEventSeqs` uniquely citing the matching `tool/call`;
     - PTC folding accepts ONLY `tool/ptc-dispatch` with `name === 'ask_user_question'`, `isError !== true`, `error === undefined`, uniquely matching `(subCallId, parentCallId, rootCallId)` (an immediate nested `memory_remember` racing ahead of async dispatch log append legitimately fails closed until settled);
     - Parses complete legacy `{ answers: [...] }` JSON (naturally skipping `dsh-spill` previews, `pending`, selected-only items, and `user-question-reply`), runs `eligibleQuestionAnswers` + `canonicalEligibleAnswersDigest`, orders occurrences by `callSeq` ascending, and assigns one shared sibling `requestId = \`q:${callSeq}:${callIdHash.slice(0, 16)}\``;
   - [owner.ts](../src/memory/node/owner.ts) verifies `owner_question_receipts` by `(session, turn, call_seq, call_id_hash)` and `answer_batch_digest` directly inside the `stageOpenTurnSources` and `settleTurn` transactions (zero extra read RPC), entering admission even when `sources` is empty (e.g., background task with `viva-task-brief` + human question answer):
     - Both paths pass typed `AnswerSource` (`custom: true`, `question`, `requestId`, `questionId`, `questionAt`, `questionProfileGen`) and pass `{ at: receipt.answered_at, timezone }` in `runtime.accept`'s **5th argument (`options`)**;
     - **Clock-rollback answer generation guard**: at first admission, if `currentDelGen > 0` and `(receipt.answer_profile_gen === null || receipt.answer_profile_gen !== currentDelGen)`, admit with `profileEligible: false` so clock rollback cannot resurrect a pre-deletion answer into L2;
     - **Persisted `eventSeq` same-turn revocation dependencies**: pass ephemeral `eventSeq` (`user/message.seq` for prompts/steers; start `callSeq` for answers) through `settleTurn` → `recordNoteRangeInTx` → `addRange`, ordering same-turn dependencies by `sourceEventSeq < answerCallSeq` rather than wall clock (keeping wall-clock `questionAt` strictly for deletion-watermark checks);
   - **Exposing question text to L2** ([memory-dream-jobs.ts](../src/memory/core/memory-dream-jobs.ts) tightened to strict `item.questionProfileGen !== delGen`):

   | Condition | Expose `question` text to L2? | Notes |
   |---|---|---|
   | No profile deletion yet (`profile_deleted_at === null && profile_deletion_generation === 0`) | ✅ **Allow** | Allowed prior to first profile deletion |
   | At least one deletion (`profile_deletion_generation > 0`) and `questionProfileGen` is missing/`null` | ❌ **Reject** (`questionUnavailable: true`) | Missing start-event generation fails closed |
   | At least one deletion and `questionProfileGen !== profile_deletion_generation` (either `<` or `>`) | ❌ **Reject** (`questionUnavailable: true`) | Mismatch in either direction fails closed |
   | At least one deletion, `questionProfileGen === profile_deletion_generation`, and `profile_deleted_at === null \|\| questionAt > profile_deleted_at` | ✅ **Allow** | Proves question was asked after the latest deletion |
   | All other cases (e.g., `questionAt <= profile_deleted_at`) | ❌ **Reject** (`questionUnavailable: true`) | Post-deletion `custom` answer itself may still be admitted while pre-deletion `question` text is withheld from L2 |
