# 架构整治：降低一次修改需要理解的范围

[English](architecture-health.md) | 简体中文

审查基线：2026-11-06，main `26e4db4`（PR #95）。这是源码与变更历史审查，不是运行性能评测。第一批保持产品行为和现有进程边界。

## 证据与优先级

产品的 `src`、`plugins` 中有 243 个 TypeScript/JavaScript 文件、30,521 行（含空行、注释和翻译，不含依赖、测试、图片、CSS）。体量本身不足以解释开发速度；更明显的问题是职责和修改集中。

| 优先级 | 证据 | 对修改的影响 | 整治方向 |
| --- | --- | --- | --- |
| P1 | `src/backend/compose.ts` 1,105 行、55 个不同的本地依赖；最近 50 个非合并提交中修改了 25 次 | 配置卡片、会话生命周期、历史切换、记忆轮询、定时与进程装配共享闭包，修改一个功能要重新理解其它功能的初始化顺序 | 让功能模块拥有业务操作和状态；入口保留创建、连接与销毁 |
| P1 | `src/renderer/app.ts` 1,103 行、43 个本地依赖；同一批提交修改了 15 次 | 页面绑定、发送与插话、卡片响应、事件分派混在一起，发送竞态只能通过整个页面排查 | 将对话副作用抽成可注入依赖的 actions；页面入口负责连接 |
| P1 | `globals.d.ts` 的 `Action`、`Untyped`、部分 IPC 返回值使用 `any`；`acp-bridge.ts` 也有开放字段 | 重构时，错拼 action 或跨模块数据形状变化可能绕过类型检查 | 先补每个功能的 action/event 联合和 IPC 结果，不一次替换全局状态类型 |
| P2 | `view/render.ts`、`view/hub.ts` 从可执行入口 `app.ts` 引入 `Dom` 类型 | 形成类型依赖回环；改页面启动会影响 view 的契约。它不是运行时循环 | 把 DOM 契约放进可独立导入、无模块级启动副作用的页面绑定模块 |
| P2 | 架构文档仍写 793 个单测，基线实际为 919；旧的重连限制也未同步 B2 | 开发者和模型会按过时描述重新调查或重复设计 | 文档描述机制，具体数量以测试输出为准；修正重连限制 |

已有值得保留的边界：shell/backend 分离，IPC 入参契约，任务状态只有 TaskRuntime 一个写入方，存储变化与事件同事务，以及 renderer 的 state/actions/view 分层。整治应沿用它们，不另建第二套任务调度或状态权威。

## 第一批已经落地的边界

- `src/renderer/conversation-actions.ts`：普通问题、图片、插话、轮次结束后的重送、反问和凭据响应。只依赖窄 API、状态访问、dispatch 和 UI 回调；不依赖 `document` 或 `app.ts`。
- `src/renderer/page-elements.ts`：一次绑定页面元素并导出 `Dom` 类型。view 不再反向依赖应用入口。
- `src/backend/config-actions.ts`：模型通过已批准的卡片执行 MCP/技能操作。依赖配置存储、技能根目录、回收站能力和变更回调；不依赖后端启动或 ACP 进程。准备卡片不写存储，成功写入后才标记 MCP 需要重载。
- `test/module-boundaries.test.ts`：扫描真实 TypeScript 语法树（含类型导入、重导出和字面量动态导入），禁止功能模块导入应用组装入口，并拒绝源码依赖环。现有后端/Electron 边界检查继续保留。

入口的行数变为 `compose.ts` 1,041、`app.ts` 943。总文件数会增加，工厂装配也仍需导入各功能；这些不是优化目标。实质是发送竞态和配置操作可以在独立测试中验证，修改它们不再需要导入启动整个应用的入口。

新增行为测试覆盖：轮次刚结束时插话改走下一问、多个插话只重送一次、失败消息保留、错误后清除待重送内容、图片发送限制、问题/凭据的 request id、凭据不进页面状态、配置预检查无写入、密钥仍加密、修改失败不触发重载、导入与技能回收。

## 后续批次与交付标准

| 顺序 | 范围 | 完成条件 |
| --- | --- | --- |
| 2 | 后端会话生命周期：启动、崩溃退避、停止、generation 隔离；随后是历史/目录切换 | 该模块独占运行状态和计时器；通过窄能力调用配置/历史；独立验证旧 generation 被丢弃、停止不再自启、切换失败恢复；compose 只装配 |
| 3 | renderer 的事件入口和对话 action 类型 | 用可穷举联合表示收到的事件和对应 action；未知事件在边界明确处理；只改前台事件不必改后台任务 reducer；保留“新话题准备中丢弃旧前台推送”测试 |
| 4 | ACP 主对话与后台会话的内部职责 | 先明确两者共用的 transport、权限和取消能力，再抽会话控制；保持进程所有权、任务运行准入和 TaskRuntime 单写入，不复制状态机 |
| 5 | 测试反馈与依赖清理 | 提供按功能执行的短反馈路径；全量及两端冒烟保持最终闸门；删除确实没有调用方的旧接口，保留契约与故障测试 |

每批只改一个可解释的职责，先确定状态由谁拥有，再移动行为及其测试，最后删除旧入口。文件拆小或改扩展名不能单独作为完成依据。第一批未修改 IPC、数据库格式、任务生命周期或 ACP 语义；后续这些边界如需改变，应单独评审和验证。

## 怎么判断是否变快

基线本地完整测试：919 项通过，约 14.8 秒（本机、现有依赖、一次测量）。这不包含两平台 CI 的机器排队、依赖安装、构建、打包和冒烟；等待远程 CI 与源码理解成本要分别记录。

每批记录四项：一次代表性功能修改涉及哪些模块、入口是否仍承载该功能的业务逻辑、针对性测试耗时、完整检查结果。第一批的两个功能模块及架构守护测试可直接执行：

```sh
npx cross-env ELECTRON_RUN_AS_NODE=1 electron --test test/conversation-actions.test.ts test/config-actions.test.ts test/module-boundaries.test.ts
npm run typecheck
```

最终验收继续运行 `npm test`、`npm run check:i18n`；重大架构改动先本地 build 和完整 smoke，再看 PR 当前提交的 macOS/Windows CI。没有完成同类修改的前后对照前，不承诺开发速度提升百分比。
