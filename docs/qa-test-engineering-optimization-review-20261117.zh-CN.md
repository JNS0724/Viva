## TEO-01 默认 unit 缺少分类防漏门槛

方案规定仅显式登记 `io / process / perf`，其余文件默认归入 `unit`，并计划让 `unit` 只在 macOS 运行。两项规则组合后，新增使用真实文件、SQLite 或 Backend 的测试只要忘记登记，就会被当成单平台纯逻辑测试；“每个文件恰好归类一次”和类别数量检查仍然能够通过。

当前[选择器](../scripts/test-feature.ts)第 35–44 行要求每个文件有且仅有一个显式成本层级。[选择器测试](../test/test-feature.test.ts)也覆盖了新增文件未登记时必须失败的情况。本轮直接调用现有审计，结果为：

```text
Discovery audit: 294 files passed
Test ownership audit failed:
test/model-new.test.ts: expected one level, found 0
```

其中 `model-new.test.ts` 是传给审计函数的虚拟路径，没有创建文件。它能匹配现有 feature 规则，失败原因仅为缺少成本分类。默认 `unit` 会移除这道检查，但不会自动证明测试没有文件或进程语义。

**建议：**保留新增文件的显式分类要求；如需减少名单维护成本，可以调整登记形式。若继续使用默认层级，未审定文件应默认双平台执行，只有明确审定为纯逻辑的测试才能参与平台去重。

**验收要求：**新增一个未登记、feature 可识别的测试路径时，分类审计必须失败，或该测试必须进入双平台集合；不得在审计全绿的情况下自动成为仅 macOS 执行的 `unit`。同时保留 JS/TS 发现完整性与重复分类检查。

## TEO-02 功能超时契约应保留在 PR 检查

方案把“真实长时限”纳入仅专项、定期或发布前运行的 `perf`。当前 [timing 分类](../scripts/test-levels.ts)第 302–304 行只有 `backend-wire-timing`，而[对应测试](../test/backend-wire-timing.test.ts)验证两项功能契约：

1. 连接空闲 5.5 秒后，RPC 仍然能够成功调用。
2. 前序请求序号缺失时，后续请求等待约定期限后能够放行，而非永久堵塞。

它们验证连接和请求顺序的正确性，并非性能基准。若按当前方案把这类测试移到 `perf`，普通 PR 对 RPC 服务的修改就可能在缺少上述回归检查的情况下通过。

**建议：**按验证目的区分功能时限与性能基准，明确将 `backend-wire-timing.test.ts` 保留在双平台 `process` 层。其他涉及取消、恢复、请求屏障和超时放行的测试同样不能仅因等待时间长而移出 PR。

**验收要求：**普通 PR 的双平台执行清单必须包含上述两个测试。移到 `perf` 的场景需要逐项说明其基准性质，以及普通 PR 保留的正确性断言；不能直接将旧 `timing` 整类迁移为 `perf`。

## TEO-03 统一测量口径并更新场景清单

方案引用的[最新 Windows headless 日志](https://github.com/JNS0724/Viva/actions/runs/44060528772/job/133961078568)与当前表格有两处明显差异：

| 指标 | 方案记录 | 日志核对结果 |
| --- | --- | --- |
| Windows `npm test` | 12 分 57 秒 | 测试步骤约 11 分 15 秒；Node runner 报告 `duration_ms 669313.2206`，约 11 分 9 秒 |
| `memory-handoff` | 27 个场景，累计约 353 秒 | 38 个场景，case duration 累计约 485.473 秒 |

12 分 57 秒接近整个 headless job 的耗时，包含测试以外的准备与检查，不能标为 `npm test`。同一运行的[macOS memory integration 日志](https://github.com/JNS0724/Viva/actions/runs/44060528772/job/133961078538)报告 `3 passed (4.0m)`；方案中的“约 5 分钟”也更接近 job 总耗时。

`memory-handoff` 的统计按日志中该文件的首个场景到最后两个 recall 场景逐项核对，共 38 个场景；485.473 秒是这些 case duration 的合计，不是文件墙钟时间。不同并发文件的 case duration 合计也不能直接相加作为 job 耗时。

这些偏差不改变 Windows headless 是主要瓶颈的判断，但会影响分片平衡、覆盖清单和阶段收益比较，尤其不能用 27 个场景作为拆分后覆盖完整的依据。

**建议：**在 PR 0 按同一提交重新生成文件与场景清单，明确记录提交、运行、平台和统计口径。分别保存 workflow 总耗时、job 耗时、测试步骤耗时、文件墙钟与 case duration 合计；历史对照使用同一口径。

**验收要求：**以当前 38 个 `memory-handoff` 场景建立名称清单，拆分前后的场景集合保持一致；分片平衡使用实际文件关键路径数据。第 2 节的 p50/p95 目标必须说明比较哪一层耗时，不得把移出 job 的环境准备时间计作测试执行优化收益。
